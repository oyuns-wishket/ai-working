## 사각지대 / 계획

- **같은 입력에서 두 스킬의 판정이 갈린다.** 수정 전 `references/standalone-visuals.md`는 덱 정본을 마스터 슬라이드·`DECK.md`로만
  정의했다. 표준 덱 스킬의 규격(규격 문서 + 그대로 찍어 내는 템플릿·빌더)은 그 정의에 들어가지 않아, 표준 덱을 만들 때마다 `new`로 판정되고
  인터뷰 두 번·시각 방향 세 개·고해상도 시안 세 개가 요구된다. 덱 스킬은 반대로 새 시안을 만들지 않는다고 적는다.
- 덱 스킬 쪽 선언만으로도 판정은 정해지지만, 정본이 그 선언과 다른 말을 하면 읽는 순서에 따라 결과가 달라진다. 정본을 함께 고친다.
- 규격을 정본으로 인정하는 문장이 게이트 우회로가 될 수 있다. 브랜드 가이드만 있는 경우와 구분하는 기준을 함께 적는다.
- 다른 세션의 미커밋 변경이 README·HANDOFF·CI workflow 에 있다. 보존하고 같은 파일에는 줄만 추가한다.
- 계획: 소유 파일(`standalone-visuals.md`)에 절 추가 → 같은 판정을 반복하는 `mode-selection.md` 갱신 → `SKILL.md` 규칙 소유 표 갱신 →
  검증기·테스트 → 독립 시나리오 검토 → 설치 연결 확인.

## 변경

- `skills/design-workflow/references/standalone-visuals.md`
  - 모드 판정 표에 행 추가: 호출한 스킬·프로젝트가 덱 규격을 제공하면 `small-feature`.
  - 덱 규격을 덱 정본과 동등한 문서로 정의하고, 색·서체·로고만 정한 브랜드 가이드는 덱 규격이 아니라고 명시.
  - `## 표준 덱 스킬과 함께 쓸 때` 절 추가: 값/절차 분담, 모드, 재사용 근거, 규격 밖 장표, 도구, 검증, 표준을 바꾸는 요청, 기록.
- `skills/design-workflow/references/mode-selection.md`: 판정 표의 덱 행과 "발표덱 만들어줘" 모호 사례를 같은 판정으로 갱신.
- `skills/design-workflow/SKILL.md`: `## 규칙 소유` 표의 덱 행에 "표준 덱 스킬과의 역할 분담"을 추가.
- `README.md`, `docs/handoff/HANDOFF.md`: 이력 링크와 현재 상태.

## 판단 근거

- **새 스킬을 만들지 않고 소유 파일을 넓혔다.** 덱 판정은 이미 `standalone-visuals.md`가 소유한다. `## 규칙 소유`의 "새 규칙은 소유 파일에
  먼저 쓰고 SKILL.md 에는 요지와 링크만"을 따랐다.
- **조직 이름을 쓰지 않았다.** 이 저장소는 공개 정본이고 표준 덱 스킬은 다른 저장소가 소유한다. "표준 덱 스킬"이라는 역할로만 적어
  다른 조직·다른 표준에도 같은 규칙이 적용된다.
- **덱 규격의 기준을 장표 구성으로 잡았다.** 프레임·레이아웃·컴포넌트를 정하고 그대로 찍어 내는 템플릿·빌더가 있어야 "기존 마스터 슬라이드
  복제"가 성립한다. 색·서체만 있는 브랜드 가이드는 장표 구성을 정하지 않으므로 기존 판정(`new`)을 그대로 둔다.
- **게이트는 면제하지 않는다.** 규격에 유형이 없어 직접 그리는 장표는 기존 새 표현 판정을 그대로 받고, 새 표현이면 시안 세 개와 사용자 결정이
  필요하다. 표준의 색·서체·톤을 바꾸는 요청은 `rebrand`·`new`다.
- **승인의 정의를 넓히지 않았다.** 초안은 "그 표준으로 만들라는 요청 원문"도 사용자 결정으로 본다고 적었으나, `SKILL.md`의 승인 정의
  (산출물을 본 뒤의 메시지)에 없는 해석이라 뺐다. 기록은 기존 세 분기 이름을 그대로 쓴다.
- **QA 스크립트 통과를 전 페이지 검사 완료로 적지 않게 했다.** 확인한 표준 덱 스킬의 스크립트는 overflow·제목 줄 수·폰트·콘솔 오류·외부
  리소스만 본다. 원본 대비 수치, 넘김·발표 동작, reduced motion, export 다시 열기는 스크립트 밖이다.
- 기각한 대안
  - 덱 스킬 쪽 선언만 두고 정본은 그대로 두기: 두 문서가 다른 판정을 적은 채로 남는다.
  - `design-workflow`가 덱 스킬을 부르기: 요청한 방향과 반대이고, 범용 절차 스킬이 특정 조직의 스킬에 의존하게 된다.
  - `SKILL.md` 본문에 절 추가: 소유 파일 원칙에 어긋나고 본문이 이미 길다.

## ⚠️ DEVIATION

- ⚠️ 별도 worktree 없이 primary checkout 에서 고쳤다 → 대응: 두 에이전트의 스킬 링크가 이 checkout 을 가리켜 다른 worktree 의 수정은
  실행 환경에 반영되지 않는다. 개인 동기화 저장소의 main 직접 반영 예외에 해당한다 → 리뷰: 자체 확인.
- ⚠️ 회사 플러그인 마켓플레이스에 있는 `design-workflow` 배포본은 고치지 않았다 → 대응: 그 배포본은 이 정본과 이미 내용이 갈라져 있고
  (절 구성과 참조 파일 수가 다르다) 스스로를 정본으로 적는다. 고치려면 게시된 플러그인의 버전을 올려야 해 이번 요청 범위를 넘는다.
  표준 덱 스킬이 자체 선언에서 "그 스킬의 문서가 덱 정본을 마스터 슬라이드·DECK.md 로만 적고 있어도 같다"고 적어 배포본만 설치한 사용자도
  같은 판정에 이르게 했다 → 리뷰: 사용자 결정 필요(후속).

- 실제 호출 확인: 새 세션의 에이전트에게 표준 덱 3장을 요청했다. 표준 덱 스킬 다음에 `design-workflow`를 불렀고 `small-feature`로 판정해
  시안 없이 만들었다. 다만 시작할 때 판정 한 줄을 알리지 않고 기록에만 남겼다. 이 실행은 아래 검토 반영 전의 문구로 돌았다.
- 독립 검토(읽기 전용, 시나리오 9개): 표준 유형만 쓰는 덱, 브랜드 가이드만 있는 경우, 면제 요청, QA 통과만으로 완료 보고하는 경우는 한 가지
  결론이 나왔다. 나머지에서 나온 지적을 아래처럼 반영했다.
  - 덱 정본의 괄호 정의에 덱 규격이 빠져 표준 덱이 `new` 행에도 걸렸다 → 정의에 덱 규격을 넣고 정의를 한 곳(`standalone-visuals.md`)에만 두었다.
  - "프로젝트가 제공하는 규격"에 조건이 없어, 에이전트가 예전 덱 파일에서 규격 문서를 먼저 써 두면 게이트가 `N/A`가 됐다 → 제공 주체를 호출한
    스킬로 좁히고 "이 작업 전부터 제공", "작업 중에 쓴 규격 문서는 아님"을 넣었다.
  - 직접 쓰는 장표의 새 표현 기준이 앱 전제뿐이었다 → 규격이 구성까지 정했고 값만 채우는 경우만 새 표현이 아니라고 적었다.
  - 색 변경 요청의 모드가 두 문서에서 달랐다 → 이 절은 모드를 정하지 않고 기존 모드 판정으로 돌려보내게 했다.
  - 규격 문서를 "기록 위치"로 적으면 승인된 것처럼 보였다 → 규격 문서는 사용자 결정 기록이 아니라고 명시했다.
  - 규격 자산에서 나온 결함의 처리 지시가 없었다 → 산출물을 손으로 고치지 않고 보고하게 했다.
- 반영 뒤 위 명령을 다시 실행해 같은 결과를 확인했다. 반영 뒤 문구로 새 세션 실행은 다시 하지 않았다.
