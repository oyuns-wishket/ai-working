# ERP 공통 도메인 지식

> **여러 ERP 프로젝트에 공통으로 적용되는 도메인 지식·체계·패턴**을 여기 모은다.
> - **올리기**: 프로젝트 작업 중 "이건 다른 ERP에도 통용된다" 싶은 개념·규칙·패턴이 나오면 → 여기 추가.
> - **참고**: 새 프로젝트/기능 시작 시 여기 먼저 읽어 공통 모델을 재사용(매번 재발명 금지).
> - **경계**: 특정 고객사 전용 규칙·수치는 여기 X → `<project>/docs/erp-domain/`(프로젝트 종속).
> 정본: `ai-working/workspaces/project-root/erp-domain.md`. bootstrap이 구성된 프로젝트 workspace에 연결한다.

## 핵심 도메인 영역 (공통 개념 — 영역별로 채운다)

### 단가/가격 체계
- (예: 입고단가 → 도매 N단계, 거래처 유형별 적용가. 프로젝트별 단계 수·수치는 각 프로젝트로.)
- 주문상품 연결에 쓰는 원천 판매가는 저장된 중간 큐 값만 신뢰하지 않는다. 값이
  없거나 0 이하이면 원천 주문에서 상품·옵션 식별키 우선순위로 다시 계산하고,
  같은 최우선 식별 후보에 서로 다른 가격이 있으면 임의 선택하지 않고 확인
  필요로 닫는다(fail-closed).
- 가격의 `유효` 판정은 효력발생일만 보지 않는다. 업무 기준 시간대의 오늘,
  진행 상태, 종료일, 판매가 존재, 양수 매입가 등 실제 저장·후속 업무가 요구하는
  조건을 조회 라벨과 저장 검증에서 동일하게 적용한다.

### 거래처 / 채널

### 주문 / 전표 / 정산
- 주문의 `품목수`는 서로 다른 라인 수(`COUNT`), `총수량`은 라인 수량 합(`SUM(qty)`)이다. 목록·KPI·전표에서 둘을 같은 값으로 취급하지 않는다.
- 특정 배치 전체 처리의 쓰기 범위는 현재 화면 페이지나 체크박스 배열로 정하지
  않는다. 서버가 확정된 배치 키와 업무 탭으로 대상을 다시 조회하며, 검색어는
  조회 조건일 뿐 전체 처리 범위를 암묵적으로 바꾸지 않는다.
- 주문→반품·교환→ERP 전표 경로에서는 요청 수량을 1로 재생성하지 않고 정본 주문 라인의 수량을 끝까지 승계한다.
- 반품·교환 접수 수량은 클라이언트 값을 그대로 신뢰하지 않는다. 서버에서 배송완료 상태·주문 소유권·품목 포함 여부·양의 정수·주문수량 이내 여부를 다시 검증한다.
- 동일 주문·품목의 반품과 교환은 합산해 주문수량을 넘지 않아야 한다. 앱 사전검증만으로는 동시 요청을 막지 못하므로 DB에서 주문 행을 잠그고 누적 수량을 다시 검사한다.
- 반품 전표는 음수 상품 크레딧 라인과 양수 공제/조정 라인(예: 고객 귀책 운반비)이 함께 존재할 수 있다. 과다반품 가드는 음수 상품 라인만 누적 검증하고 양수 조정 라인은 판매수량 검사에서 제외한다.
