# 기능 명세 템플릿

> 이 템플릿은 6단계 "기능 명세" 작성을 안내한다.
> 목표 분량: 필수 섹션(1~8) 4,500~7,000 토큰 / 조건부 포함 시 7,000~10,000 토큰
> 최소 분량: 4,000 토큰 미만이면 섹션 누락으로 판단하고 보완 요청
> 최대 분량: 12,000 토큰 초과 시 기능 분할 검토
> 의존:
>   - 해당 기능의 `docs/specs/features/{NN}-{page-name}/{MM}-{feature-name}.md`를 Read
>   - 해당 페이지의 `docs/specs/page-specs/{NN}-{page-name}/00-page-spec.md`를 Read
> 반복 단위: 기능 1개 = 기능 명세 1파일

## 산출물 경로

`docs/specs/feature-specs/{NN}-{page-name}/{MM}-{feature-name}.md`

## frontmatter

```yaml
---
title: "{기능 제목}"
stage: "feature-spec"
depends-on:
  - "docs/specs/features/{NN}-{page-name}/{MM}-{feature-name}.md"
  - "docs/specs/page-specs/{NN}-{page-name}/00-page-spec.md"
created-at: YYYY-MM-DD
status: draft
---
```

## 필수 섹션 (1~8, 모든 기능에 필수)

기능 정의의 설명·컴포넌트 힌트와 페이지 명세의 레이아웃·상태 관리를 참조하여 작성한다.

### 섹션 1: 개요

```markdown
## 1. 개요
- **해결하는 문제**: (현재 문제 상황을 구체적으로. "~이 불편하다" 수준이 아니라 "~로 인해 월 N시간의 비효율이 발생하고, ~오류가 발생한다" 수준으로)
- **제공하는 가치**:
  - (가치1 — 정량적 효과 포함)
  - (가치2)
- **범위**:
  - **다루는 것**: (포함 항목 bullet list)
  - **다루지 않는 것**: (제외 항목 + 괄호로 해당 기능 위치 참조. 예: "계약 승인 처리(계약 승인 페이지)")
```

### 섹션 2: 사용자 스토리 + 인수 조건

```markdown
## 2. 사용자 스토리 + 인수 조건

### US-1: {스토리 제목}
As a **{역할}**, I want **{행동}**, so that **{가치}**

**인수 조건:**
- [ ] AC-1: (구체적, 검증 가능. 수치·동작·상태 변화를 명시. 예: "클릭 시 500ms 이내 렌더링", "상태가 PENDING에서 APPROVED로 전환")
- [ ] AC-2: ...
```

US당 최소 3개 이상의 AC. 각 AC는 개발자가 자동화 테스트로 검증 가능한 수준으로 작성.

### 섹션 3: UI/UX 명세

```markdown
## 3. UI/UX 명세

### 컴포넌트 계층
```
PageComponent

│   ├── Breadcrumb ("경로 > 표시")
│   └── ActionBar

│       └── Button ("액션명", variant: secondary)
├── MainContent

│   │   └── ...
│   ├── DataTable
│   │   └── TableRow
│   └── EmptyState
└── SidePanel (조건부)
```

### 5가지 화면 상태
| 상태 | 조건 | UI 표현 | 사용자 액션 |
|------|------|---------|------------|
| Empty | (데이터 0건 조건) | (구체적 UI) | (사용자가 할 수 있는 행동) |
| Loading | (API 호출 중) | (스켈레톤/스피너 상세) | (대기 중 가능한 액션) |
| Partial | (일부 데이터만 로드) | (어떤 부분이 불완전한지) | ... |
| Error | (API 실패 조건) | (에러 UI 상세) | (재시도 방법) |
| Ideal | (정상 데이터 존재) | (완전한 UI 상세) | (모든 가능한 액션) |

### 반응형 대응
- **Mobile (< 768px)**: ...
- **Tablet (768px ~ 1024px)**: ...
- **Desktop (> 1024px)**: ...

### 인터랙션 상세
| 인터랙션 | 동작 |
|----------|------|
| {사용자 액션} | (디바운스, 애니메이션, 확인 다이얼로그 등 구체적 동작) |

### 시각 디자인 스펙 (해당 시)
| 상태/카테고리 | 배경색 | 텍스트색 | 아이콘 |
|-------------|--------|----------|--------|
| ... | #HEX | #HEX | 아이콘명 |
```

5가지 화면 상태는 **모두 필수**. "해당 없음"은 허용하지 않는다 — 모든 UI에는 Empty, Loading, Error 상태가 존재한다.

### 섹션 4: 데이터 모델

```markdown
## 4. 데이터 모델

### {테이블명} 테이블
| 필드명 | 타입 | 제약조건 | 인덱스 | 설명 |
|--------|------|----------|--------|------|
| id | UUID | PK, DEFAULT gen_random_uuid() | PK | 고유 식별자 |
| ... | ... | ... | ... | ... |

**CHECK 제약조건 (테이블 레벨):**
```sql
CHECK (조건)
```

### 복합 인덱스
| 인덱스명 | 컬럼 | 용도 |
|----------|------|------|
| ... | ... | ... |
```

기존 테이블 수정인 경우 변경 사항만 명시. 신규 테이블은 전체 스키마를 작성.

### 섹션 5: API 명세

```markdown
## 5. API 명세

### {METHOD} {path}
(API 설명 한 줄)

**요청:**
```typescript
interface {Name}Request {
  field: type;      // 설명, 제약
}
```

**응답 {statusCode}:**
```typescript
interface {Name}Response {
  field: type;      // 설명
}
```

**에러 코드:**
| 코드 | 상황 | 메시지 |
|------|------|--------|
| 400 | ... | "사용자에게 보여줄 메시지" |
| 404 | ... | ... |
| 500 | ... | ... |
```

각 API 엔드포인트마다 요청/응답 TypeScript interface와 에러 코드 테이블을 **빠짐없이** 작성한다.

### 섹션 6: 비즈니스 로직

```markdown
## 6. 비즈니스 로직

### 핵심 로직 상세
(분기 조건 테이블, 계산 로직, 자동 채번, 역할별 동작 차이, 상태 전이 다이어그램 등)

### 유효성 검사
| 필드 | 규칙 | 에러 메시지 |
|------|------|------------|
| {필드명} | (구체적 규칙) | "사용자에게 보여줄 메시지" |

### 엣지케이스
- **케이스 1**: (상황 설명) → (시스템 대응 방식)
- **케이스 2**: ...
```

엣지케이스는 최소 3개 이상. "동시 수정", "데이터 불일치", "권한 변경" 등 실제 운영에서 발생 가능한 시나리오를 다룬다.

### 섹션 7: 상태 관리

```markdown
## 7. 상태 관리

### 클라이언트 상태

```typescript

  queryKey: ['key', params],
  queryFn: () => fetchData(params),
  staleTime: 30_000,        // 30초 — 근거
  gcTime: 300_000,          // 5분
  enabled: !!requiredParam, // 조건
});
```

### 낙관적 업데이트
- (적용 여부 및 전략. 읽기 전용이면 "해당 없음 — 읽기 전용 기능"으로 명시)
```

### 섹션 8: 에러 처리

```markdown
## 8. 에러 처리
| 시나리오 | 에러코드 | 사용자 메시지 | 복구 전략 |
|----------|----------|--------------|----------|
| 네트워크 오류 | NETWORK_ERROR | "..." | (자동 재시도, 재시도 버튼 등) |
| 인증 만료 | 401 | "..." | (리다이렉트, 데이터 보존 등) |
| 서버 오류 | 500 | "..." | (재시도 횟수, 폴백 등) |
```

"복구 전략"은 사용자가 어떻게 정상 상태로 돌아올 수 있는지를 구체적으로 기술한다.

## 조건부 섹션 (9~14)

아래 섹션은 조건에 해당할 때 작성한다. 조건에 해당하는데 누락하면 품질 게이트에서 경고한다.

| 섹션 | 조건 |
|------|------|
| 9. 페이지 내 연관 기능 | 동일 페이지에 기능이 2개 이상 |
| 10. 크로스 페이지 의존성 | 다른 페이지와 데이터 흐름 존재 |
| 11. 이미지 에셋 요구사항 | 커스텀 아이콘/일러스트 필요 |
| 12. 테스트 계획 | 복잡도 medium 이상 |
| 13. 성공 지표 KPI | 핵심 기능, 비즈니스 임팩트 측정 필요 |
| 14. 복잡도+MVP | 복잡도 high 또는 MVP/Full 구분 필요 |
