# Jump Desktop on a new Mac

Use this procedure when Jump Desktop is explicitly selected or discovered on the baseline device. Official product and support entrypoints: https://jumpdesktop.com/ and https://support.jumpdesktop.com/. Verify current distribution, license and activation instructions there before installing or transferring a purchase; do not encode old pricing or trial notes as current entitlement.

1. Discover host/viewer roles. Inspect installed app bundle identifiers/versions, supported local settings and Jump-related service registration. Jump Desktop is the viewer client; Jump Desktop Connect is the host component. Install the component needed by each device through its supported channel, including both only if the device serves both roles.
2. For the viewer, determine the actual purchase channel and activation status: Mac App Store purchase, direct purchase/license, managed team access or trial. A Connect installation, installer download or old note is not evidence of a paid client license. An App Store receipt is not a reusable direct-purchase license key. If no key can be verified, report that precisely and follow the applicable account/purchase route.
3. For the host, connect the selected account/device with the intended permissions. Preserve existing connections and services. Browser login and macOS Screen Recording, Accessibility or other required GUI permissions remain user steps; perform supported terminal configuration directly.
4. Test a real connection between the intended devices, resolution/HiDPI, Korean/English input, selected clipboard behavior and reconnection. Use the existing remote-setup display/input helpers only when compatible with the observed setup. Do not assume the same settings work for every client version.
5. If the user explicitly requests a personal license investigation, search relevant app preferences/support data, receipts, purchase documents and selected local backups without exposing keys or authentication values in output. Expand to personal text/history only when authorized. Inspect protected stores through supported targeted access, never a blanket Keychain export. Keep evidence and candidate values in restricted machine-local storage outside Git; distinguish historical references from verified entitlements.
6. If the user explicitly asks to save to a personal password manager such as 1Password, use its supported authenticated integration. Find the existing matching item before creating a duplicate; resolve the intended personal vault if ambiguous. Pass sensitive fields via protected JSON/stdin rather than shell arguments. Save confirmed keys as concealed fields with purchase channel/source and verification notes; keep unverified candidates labeled and never invent a key. Verify the saved item through a readback without printing its secret values, then remove temporary secret payloads. If authentication is unavailable, complete the investigation and report the exact remaining access step. This opt-in personal workflow does not authorize customer-project credential retrieval.

Report client and host installation separately, purchase/activation evidence, verified remote behavior and remaining login/permission actions. Keep all personal license values, account names and device identities out of the public skill repository.
