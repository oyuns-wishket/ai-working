## 필수 섹션 및 작성 가이드

### 1. 메뉴 구조 개요 (3레벨: 섹션 → 모듈 → 메뉴)

> **메뉴는 3레벨 트리다** (erp-core 표준 — `level ∈ {section, module, menu}`):
> - **섹션(section)** = 대분류 (예: 영업, 회계, 시스템 관리) — 사이드바 최상위 그룹
> - **모듈(module)** = 중분류 (예: 고객, 매출, 권한관리) — 섹션 안의 묶음
> - **메뉴(menu)** = 실행 메뉴 = 클릭 가능한 라우트 (예: 고객 목록, 사용자관리)
>
> 클릭 가능한 라우트는 보통 **menu 레벨**. 이 3레벨이 그대로 gen-app의 사이드바(섹션 헤더 → 모듈 그룹 → 메뉴 링크)가 된다. 2레벨만 있는 단순 시스템이면 섹션 1개로 시작하되 구조는 3레벨로 표기한다.

사용자에게 질문:
- "시스템의 메뉴를 섹션(대분류) → 모듈(중분류) → 메뉴(실행 화면) 3단계로 알려주세요."

> **검증 규칙(결정론적 — 비준수 시 보완):** 모든 메뉴 항목은 **`level`(section|module|menu)** 과 **`parentCode`(최상위 섹션만 null)** 를 가져야 한다. **section → module → menu**의 3계층이 반드시 존재해야 하며 — 즉 **모든 클릭 가능한 라우트(menu)는 어떤 module의 자식이고, 모든 module은 어떤 section의 자식**이다. **섹션 바로 아래에 메뉴(라우트)를 매다는 평탄한 2계층 트리(섹션→메뉴)는 비준수다** — module 레벨이 빠지면 gen-app 사이드바가 3단으로 렌더되지 못한다(tmax 2계층 회귀). 모듈이 곧 단일 화면이어도 module 노드를 만들고 그 아래에 menu 노드를 둔다(아래 "고객" 모듈 예시처럼 module≠menu를 유지).

#### 작성 형식 (트리 + 평면 테이블 둘 다 — 평면 테이블이 기계 판독 정본)

3계층을 사람이 읽는 트리(시각용)와 **`level`/`parentCode`/`code`가 명시된 평면 테이블**(gen-app가 `MenuItem`으로 적재하는 정본) 두 형태로 모두 작성한다.

```markdown
## 1. 메뉴 구조 개요

### 메뉴 트리 (섹션 → 모듈 → 메뉴) — 채워진 예시

(아래는 형식을 보여주는 구체 예시다. 실제 프로젝트 메뉴로 교체한다.)
```
├── [섹션] 영업 (SEC_SALES)
│   ├── [모듈] 고객 (MOD_CUSTOMER)
│   │   ├── [메뉴] 고객 목록        → /sales/customers
│   │   └── [메뉴] 고객 등록        → /sales/customers/new
│   └── [모듈] 매출 (MOD_REVENUE)
│       ├── [메뉴] 매출 현황        → /sales/revenue
│       └── [메뉴] 매출 마감        → /sales/revenue/close
└── [섹션] 시스템 관리 (SEC_SYSTEM) — §3 필수
    ├── [모듈] 권한관리 (MOD_AUTHZ)
    │   └── [메뉴] 사용자관리        → /system/users  … (§3 표 참조)
    └── [모듈] 시스템도구 (MOD_SYSTOOL)
        └── [메뉴] 공통코드관리      → /system/codes  … (§3 표 참조)
```

### 메뉴 트리 (평면 테이블 — level/parentCode 정본) — 채워진 예시

| code | name | level | parentCode | href | sortOrder | 대상 역할 |
|------|------|-------|-----------|------|-----------|----------|
| SEC_SALES | 영업 | section | (null) | (null) | 01 | 영업, 관리자 |
| MOD_CUSTOMER | 고객 | module | SEC_SALES | (null) | 01 | 영업, 관리자 |
| MENU_CUST_LIST | 고객 목록 | menu | MOD_CUSTOMER | /sales/customers | 01 | 영업, 관리자 |
| MENU_CUST_NEW | 고객 등록 | menu | MOD_CUSTOMER | /sales/customers/new | 02 | 영업 |
| MOD_REVENUE | 매출 | module | SEC_SALES | (null) | 02 | 영업, 회계 |
| MENU_REV_STATUS | 매출 현황 | menu | MOD_REVENUE | /sales/revenue | 01 | 영업, 회계 |
| MENU_REV_CLOSE | 매출 마감 | menu | MOD_REVENUE | /sales/revenue/close | 02 | 회계 |

> 위 한 줄이 erp-core `MenuItem`(§5 `MenuItemNode`)의 한 노드로 그대로 적재된다. **section/module 행은 `href`가 null**(클릭 라우트 아님, 그룹 헤더), **menu 행만 `href`를 가진다.** `code`는 트리 전역 고유. 시스템 관리 섹션의 module/menu 행은 §3 표를 그대로 채운다.

### 메뉴 요약

| 섹션 | 모듈 수 | 메뉴 수 | 주요 역할 |
|------|--------|--------|----------|
| 영업 (SEC_SALES) | 2 | 4 | 영업, 회계, 관리자 |
| 시스템 관리 (SEC_SYSTEM) | 2 | 11 | 관리자, 마스터 |
```

### 2. 메뉴 상세

각 **섹션**별로, 그 안의 **모듈 → 메뉴**를 아래 형식으로 반복한다.

```markdown
## 2. 메뉴 상세

### [섹션] {섹션명}
- **설명**: (이 섹션이 다루는 업무 대분류)
- **대상 사용자/권한**: (어떤 역할이 접근 가능한지)

#### [모듈] {모듈명}
| 순서 | 메뉴명 | 설명 | 라우트(예) | 대상 사용자 |
|------|-------|------|-----------|-----------|
| 01 | {메뉴1} | ... | /sales/customers | ... |
| 02 | {메뉴2} | ... | /sales/customers/new | ... |
```

메뉴 순서(sortOrder)를 명시한다. 이 순서가 이후 단계에서 파일명의 번호 접두사가 된다.

섹션별로 최소 1개 모듈, 모듈별로 최소 1개 메뉴를 정의한다. 모듈이 곧 단일 화면이면 "모듈 = 단일 메뉴"로 표기한다(레벨 구조는 유지).

### 3. 필수 시스템 메뉴 (무조건 포함 — erp-core baseline 앱)

> **강제 규칙(결정론적):** 1단계 계획서에 **로그인 + 역할/조직**이 있는 ERP/어드민형 앱이면, 사용자가 언급하지 않아도 **`시스템 관리` 섹션 + 그 아래 권한관리·시스템도구 두 모듈과 필수 메뉴를 전부 무조건 포함**한다(공개 사이트 등 로그인·역할이 없는 앱이면 자동 생략). 이 메뉴들은 운영 중 데이터(권한·조직·메뉴·코드)를 코드 수정 없이 편집하는 핵심 관리 화면이다. **정본은 `gen-app/references/ssot/erp-core/spec.md §1.5`** — 여기 표는 그 미러이며, 빠지면 gen-app가 강제로 다시 채운다(Phase C `check-erp-modules` 게이트가 존재 확인).
>
> **3레벨 매핑:** `[섹션] 시스템 관리` → `[모듈] 권한관리` / `[모듈] 시스템도구` → 아래 표의 각 행 = `[메뉴]`(실행 라우트). **공통 원칙:** 모든 항목은 **동적 생성/편집 가능**(코드 상수 배열 금지), 세부는 ERP 도메인에 맞춰 개발자와 협의(아래는 최소 골격).

#### [섹션] 시스템 관리 › [모듈] 3-A. 권한관리 (무조건)

| 순서 | 메뉴명 | 설명 | 대상 |
|------|-----------|------|------|
| 01 | **사용자관리** | 로그인 계정 CRUD · 활성/비활성 · 초대/비밀번호. | 관리자 |
| 02 | **사원관리** | 사원 프로필 · 소속 조직 · 직책 매핑 · 활성 사원 지정. | 관리자 |
| 03 | **조직관리** | 조직(부서/법인) **트리 계층** CRUD — 사용자가 계층을 자유롭게 추가/이동(데이터 주도). | 관리자 |
| 04 | **직책(역할)관리** | 역할(직책) CRUD. | 관리자 |
| 05 | **메뉴관리** | 사이드바 메뉴(MenuItem) CRUD · 순서 · 명칭/라벨 · 아이콘 · 표시여부 · 계층 편집. | 관리자 |
| 06 | **메뉴권한관리** | 역할(×조직)별 메뉴×액션(CRUD) 노출/접근 **매트릭스**. 형상은 gen-app A4에서 고른 §5.3 권한 모델을 따른다(기본 Option B = (역할,조직)×메뉴). UI권한·control_level 포함. | 관리자 |
| 07 | **권한그룹관리** | 권한(메뉴/액션/UI)을 묶은 권한그룹 CRUD · 역할/사용자에 할당. | 관리자 |

#### [섹션] 시스템 관리 › [모듈] 3-B. 시스템도구 (무조건)

| 순서 | 메뉴명 | 설명 | 대상 |
|------|-----------|------|------|
| 01 | **테마설정** | design-set 브랜드 토큰(**값만**) 설정. 디자인시스템 SSOT 닫힌집합 토큰·보편규칙 범위 내(체계·역할 고정). | 관리자 |
| 02 | **보안·로그 관리** | 접근/감사 로그 조회 + 보안 정책(세션·비밀번호 규칙 등) 관리. | 관리자 |
| 03 | **마스터 계정 관리** | **모든 권한을 가진 최상위(마스터) 계정** 관리(생성/위임/회수). 마스터 = 어드민 단일기준 `SYS_ADMIN`과 정합(별도 admin 판정 신설 금지). | 마스터 |
| 04 | **공통코드관리** | 공통코드(코드그룹 · 코드값 · 정렬 · 사용여부) CRUD — 드롭다운/구분값을 코드 상수 대신 데이터로. | 관리자 |

> 위 외 시스템 설정(브랜딩·세션·기능 토글)·알림 설정·데이터 마이그레이션 등은 도메인에 맞춰 개발자와 협의해 시스템도구 아래에 추가한다.
