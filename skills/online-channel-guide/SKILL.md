# Online Channel Guide

온라인채널 하나를 “API가 호출된다” 수준이 아니라 채널 관리자 화면, API, 수집 DB, ERP UI가 같은 기준으로 수렴하는 운영 가능한 상태까지 이끈다. 특정 채널의 구현을 복사하지 말고 아래 게이트를 채널별 증거로 다시 통과한다.

## 진입 라우터

사용자가 “온라인채널 주문연동 하려고 한다”고 하면 **코드를 열기 전에 Phase 0부터** 시작한다.

| 사용자가 있는 지점 | 시작 위치 |
| --- | --- |
| 아직 키·권한이 없다 / 무엇이 필요한지 모른다 | **Phase 0** + 해당 채널 카드 |
| 키는 있고 이제 붙인다 | Phase 1 |
| 이미 붙었는데 숫자가 안 맞는다 | Phase 4, 대표 재발 방지 패턴 표 |
| 발주확인·상태 전이 write | Phase 5 |
| 사라진 주문·stale 상태 | Phase 6 |
| spinner·큐가 안 끝난다 | Phase 7 |

역할 분담, 첫 호출 검증, 함정, 폴백이 들어 있다. `확인일이 90일을 넘으면 공식 문서를 재확인`한다.

| --- | --- | --- | --- | --- |

### 호스팅사·솔루션 경유 채널

직접 API가 `REVIEW`/`CONTRACT`라고 해서 그 채널이 미연동인 것은 아니다. 자사몰
호스팅사(카페24 마켓플러스 등)나 셀링툴이 그 마켓을 지원하면 **이미 그 경로로 주문이
들어오고 있을 수 있다**. 등급표는 *직접 API* 기준이므로, 착수 전에 다음을 먼저 본다.

1. 자사몰/솔루션 관리자의 **마켓 계정 연동 목록**에 그 채널이 등록돼 있는가.
2. 등록돼 있다면 그 마켓 주문이 **우리가 이미 쓰는 API 응답에 섞여 들어오는지** 실측한다.
3. 섞여 들어온다면 필요한 일은 신규 온보딩이 아니라 **채널 귀속 분류**뿐이다.

이 확인을 건너뛰면 이미 유입 중인 주문을 "미연동"으로 오판하거나, 반대로 자사몰
주문을 그 마켓 주문으로 잘못 귀속시킨다. 재발 가능한 오류는 아래 "채널 귀속" 절을 참조한다.

## 시작 규칙

1. 저장소 규칙, as-is 자료, 관련 spec·impl-note·HANDOFF를 먼저 읽는다.
2. 프로젝트에 온라인채널 가이드가 있으면 그것을 기술 정본으로 사용한다. 예: `docs/guides/online-channel/`.
3. 구현·비가역 작업이면 저장소의 이슈/브랜치/승인 절차를 따른다. `dev-protocol`, `feature-flow` 같은 별도 스킬이 있으면 함께 사용한다.
4. 사용자에게 채널 관리자 화면의 상태별 실제 숫자와 기준시각을 요청한다. 모르는 설계 결정을 한 번에 하나씩 확정한다.
5. API 정보는 최신 공식 문서를 우선 조사하고 URL·버전·확인일을 남긴다. 문서 추정과 라이브 실측을 구분한다.
6. `assets/channel-workbook-template.md`를 프로젝트 문서로 복사해 조사 결과를 채운다.
7. `assets/release-checklist.md`를 구현 계획과 완료 검증에 사용한다.

## 고정 상태 계약

통합 주문 상태는 다음 6개를 기본으로 한다.

| 상태 | 의미 |
| --- | --- |
| `PAID` | 결제 완료, 채널 발주확인 전 |
| `PREPARING` | 발주확인·상품 준비 중 |
| `SHIPPING` | 배송지시·출고·배송 중 |
| `DELIVERED` | 배송 완료·구매 확정 |
| `CANCELLED` | 취소·반품 등 주문 처리 흐름에서 종결 |
| `UNKNOWN` | 의미가 확정되지 않았거나 별도 업무 흐름 |

- 원상태는 `status`, 통합 상태는 `status_norm`, 원본 응답은 `raw`처럼 분리해 보존한다.
- 채널 상태가 더 세밀하면 원상태를 잃지 말고 UI 필터에서 필요 수준으로 노출한다.
- 교환 완료, 부분 반품처럼 6상태로 의미가 손실되면 무리하게 합치지 말고 `UNKNOWN` 또는 별도 클레임 모델로 보존한다.
- 통합 상태만 보고 비가역 write를 호출하지 않는다. 호출 직전에 채널 원상태·보조 필드·eligibility를 재확인한다.

## 채널 귀속 — 마켓·주문경로·결제수단은 서로 다른 축이다

한 API 응답에 여러 지면의 주문이 섞여 오는 경우(자사몰 + 그 호스팅사가 중계하는 마켓)
각 주문을 어느 논리 채널로 귀속시킬지 정해야 한다. 여기서 세 축을 반드시 분리한다.

| 축 | 예시 필드 | 채널 귀속 근거 |
| --- | --- | --- |
| **판매 마켓** | `market_id`, `order_place_id` 중 마켓 코드 | ✅ 이것이 기준 |
| **주문경로(order place)** | 같은 필드의 자사몰 경로 코드 | ✅ 자사몰이면 자사몰 |
| **결제수단** | `payment_method`, PG명, 간편결제 브랜드 | ❌ 기준 아님 |

**귀속 기준은 "주문서가 생성·관리되는 지면"이다.** 결제수단은 채널이 아니다.

### 판별식 — 마켓 주문의 유일한 확증

> **그 주문의 마켓 주문번호가 해당 마켓 판매자센터의 주문번호와 실제로 일치하는가.**

이 대조를 통과해야 마켓 주문이다. 코드명이나 표시명으로 단정하지 않는다.

- 마켓 주문이면 응답에 **그 마켓 판매자센터의 주문/결제번호**(`market_order_no` 등)가 담긴다.
  판매자센터 화면의 실제 번호와 자릿수·값이 일치하는지 눈으로 대조한다.
- 자사몰 간편결제 주문은 마켓 주문번호 자리에 **자사몰 형식 번호**가 들어간다.
- 결제 브랜드가 코드명에 들어가 있어도(`KAKAOPAY`, `NCHECKOUT` 등) 그것은 대개
  **자사몰 간편구매 주문경로**다. 브랜드명 ≠ 지면.

### 재발 가능한 분류 오류

카페24 주문의 `order_place_id=KAKAOPAY`를 카카오톡스토어 마켓 주문으로 오인할 수 있다.
`KAKAOPAY`는 **톡체크아웃** — 자사몰 주문서에 생성되는 카카오 간편구매였고, 진짜 톡스토어
주문은 `market_id=kakao`로 별도 유입될 수 있다. 둘을 합치면 **정확히 뒤바뀐 귀속**이 된다.

| 실제 성격 | 잘못 적재된 곳 | 정본 |
| --- | --- | --- |
| 톡체크아웃(자사몰 간편구매) | 마켓 채널 ❌ | 자사몰 |
| 톡스토어(마켓) | 자사몰 ❌ | 마켓 채널 |

해소 근거는 문서가 아니라 **판매자센터 결제번호 ↔ API `market_order_no` 교차대조**였다.
같은 층위의 네이버페이 주문형(`NCHECKOUT`)은 처음부터 자사몰로 두고 있었는데, 한쪽만
분리한 비대칭이 오류의 신호였다 — **동종 주문경로를 서로 다르게 취급하고 있다면 의심한다.**

### 귀속 매핑을 추가할 때

1. 라이브 응답에서 **실측한 코드값**만 매핑한다. 공식 문서의 값 목록이나 추측은 금지.
2. 그 코드의 표본 주문 1건을 **해당 마켓 판매자센터에서 찾아 대조**한다.
3. 매핑 상수 옆에 실측 근거(코드값·표시명·번호 형태·확인일)를 주석으로 고정한다.
4. 표시명(`order_place_name`)은 지역화·가변이라 분류 기준으로 쓰지 않는다. 근거로만 남긴다.
5. 귀속을 바꾸면 미러 테이블뿐 아니라 **편입된 canonical 주문·발주확인 이력·송장 큐**까지
   같은 기준으로 재동기한다. 한쪽만 고치면 계보가 끊긴다.

## 채널 네이티브 화면과 ERP 공통화 경계

온라인채널 연동은 한 개의 전역 상태표로 모든 화면을 통일하지 않는다. 다음 3계층을
분리한다.

1. **원천 계층** — 채널의 raw 주문상태, 클레임 유형·상태, 변경시각과 원본 응답을
   손실 없이 보존한다.
2. **채널 운영 계층** — 채널 탭의 카드·필터·목록 라벨은 해당 채널 관리자 화면의
   상태명, 날짜축, 집계 단위와 운영 단계를 따른다. 채널마다 서로 달라도 정상이다.
3. **ERP 업무 계층** — 주문·클레임을 발주처리, 수거, 정산 같은 ERP 공통 업무로
   편입하는 경계에서만 공통 상태와 eligibility로 변환한다. 이때도 원천 snapshot과
   채널 키는 감사용으로 보존한다.

채널 운영 계층의 메트릭은 아래 계약을 지킨다.

- 카드 숫자와 카드 클릭 목록은 **동일한 채널별 predicate**를 사용한다.
- `0건` 카드의 클릭 결과는 반드시 0건이어야 한다. 유형만 넓게 조회해 진행·완료
  상태를 다시 섞지 않는다.
- `claimType=EXCHANGE`처럼 업무 유형이 같아도 요청·수거중·수거완료·재배송·완료는
  서로 다른 채널 네이티브 단계다.
- 채널 API에서 입증하지 못한 관리자 전용 지표는 `0`이 아니라 미지원(`—`)으로 둔다.
- 전체 채널/발주처리 화면은 ERP 공통 업무 상태를 사용할 수 있지만, 개별 채널 탭의
  원상태 필터와 라벨을 대체하지 않는다.

## 필수 산출물

채널별로 다음 9개가 모두 있어야 완료다.

0. 온보딩 카드(신청 경로·리드타임·키 수명·IP 요건·역할 분담)
1. API·인증·고정 IP·호출 제한 조사
2. raw 상태 → 통합 상태 매핑표
3. 관리자 대시보드 ↔ API ↔ ERP 정합성 표
4. 주문 처리 전이와 write API 지도
5. terminal·unresolved 판정 정책
6. 운영 자격증명 기반 live read-only probe와 write 전 dry-run
7. 구현노트·테스트·배포·E2E 체크 결과
8. 실패와 해결책을 다음 채널 체크로 환류한 기록

하나라도 비어 있으면 `코드완료`, `live-read`, `live-write`, `운영` 중 실제 수준으로 표시하고 운영 완료라고 부르지 않는다.

## Phase 0 — 온보딩

상세는 `references/onboarding.md`. 요지는 다음과 같다.

주문연동의 첫 병목은 코드가 아니라 **자격**이다. 키가 없으면 Phase 1 이후는 전부 대기다.
따라서 **리드타임 있는 항목을 착수 첫날에 신청**하고, 코드는 그동안 fake 기반으로 병렬 진행한다.

행위자를 3분한다. `[AI]` 터미널·코드·문서 / `[USER]` 브라우저 로그인·동의·승인 /
`[3RD]` 고객사 담당자·채널 심사역처럼 우리가 통제하지 못하는 주체.
`[3RD]`가 있는 항목이 곧 일정의 종속변수다.

온보딩 등급이 일정 산정을 지배한다.

| 등급 | 의미 | 일정 특성 |
| --- | --- | --- |
| `SELF` | 판매자 화면에서 즉시 발급 | 시간~하루. 코드와 동시 착수 |
| `REVIEW` | 신청 후 채널이 심사·승인 | 며칠~몇 주. 거절·부분승인 가능 |
| `CONTRACT` | 선정·계약이 선행 | 예측 불가. 별도 사업 트랙 |

### 진입 인터뷰

한 번에 하나씩 확정한다.

1. 어떤 채널인가(복수면 전부).
2. 판매자 계정 상태 — 가입·사업자 인증·**API 발급 권한이 있는 계정 등급**인가.
3. 신청 명의 — 판매자 본인인가 솔루션사·대행사인가.
4. 호출 서버 — 고정 IP가 확보됐는가. 미프로비저닝이면 IP 화이트리스트 채널은 키가 무용하다.
5. 이번 범위 — read 수집만인가, write까지인가, 클레임·정산·문의까지인가.

### 산출: 착수 브리프

인터뷰 뒤 다음 3블록을 이 순서로 제시한다. 순서가 곧 우선순위다.

```text
A. 지금 당장 신청해야 할 것   [USER]/[3RD] 리드타임 항목, 예상 소요와 함께
B. AI가 병렬로 진행할 것      문서조사·어댑터 스켈레톤·fake 테스트·매핑 초안
C. 키 도착 후 착수            Phase 1~8
```

A가 비면 그날 Phase 1로 넘어간다. A에 `CONTRACT`가 있으면 **폴백을 함께 제시**하고
승인을 기다리며 범위를 비워두지 않는다.

자격증명은 값이 아니라 **보관 위치만** 기록한다. 만료가 있는 키(1년·180일 등)는
발급 즉시 만료일을 운영 캘린더·모니터링에 등록한다. 만료 사고는 조용한 수집 0으로 나타난다.

## Phase 1 — 원천과 범위 고정

먼저 다음을 확정한다.

- 판매자 계정·스토어 식별자, 관리자 화면 타임존과 기준시각
- 이번 범위: 주문 read, 대시보드, 발주확인, 송장, 문의, 클레임 중 무엇인지
- 관리자 화면이 세는 단위: 주문, 배송그룹, 상품라인, 수량
- 화면 숫자의 조회기간: 오늘, 최근 N일, 누적, 최종변경일
- 향후 취소·반품·교환 상세 연결을 위해 지금 보존할 키와 raw/audit

사용자와 AI 역할은 다음처럼 나눈다.

| AI | 사용자 |
| --- | --- |
| as-is·코드·문서 조사, 공식 API 확인, 상태/키 매핑, read-only probe, 구현·테스트·dry-run, 문서화, 승인된 배포 검증 | 판매자 화면 스크린샷과 실제 숫자, OAuth/IP/로그인 GUI, 운영 write·migration·commit/push 승인, 최종 UX 확인 |

## Phase 2 — API와 식별자 조사

공식 문서와 live read-only 응답으로 다음을 기록한다.

- 인증 방식, token 수명·회전, 재동의, 고정 IP
- endpoint, method, pagination, 최대 조회기간, batch 크기, rate limit
- 날짜 포맷, 타임존, 경계 포함 여부
- 주문·배송그룹·라인·클레임 자연키
- 상태가 order/item/shipment 중 어느 레벨에 붙는지
- 생성일·변경일·상태별 current list 중 어떤 조회가 가능한지

합성 키는 마지막 수단이다. 페이지 순서나 배열 index처럼 재조회 때 달라질 수 있는 값에 의존하지 않는다. 확정할 수 없으면 팬텀 행을 만들기보다 fail-closed하고 blocker로 기록한다.

## Phase 3 — 상태 매핑과 수집 전략

raw 상태마다 관리자 화면 라벨, 통합 상태, live 표본을 매핑한다. 모든 미확정 값은 `UNKNOWN`으로 보존하고 운영 알림 대상으로 둔다.

수집 경로는 역할을 분리한다.

```text
incremental         신규 주문·변경 이벤트를 낮은 지연으로 수집
on-demand           탭 진입·주문수집·새로고침 요청을 최신화
periodic backstop   최근 기간을 다시 훑어 과거 주문의 상태 전이 보완
terminal reconcile  현재 목록에서 사라진 활성 주문을 명시적 증거로 재판정
```

생성일 기반 API는 과거 주문의 이후 상태 변경을 놓칠 수 있다. 이 경우 상태별 current list, 변경일 API, 최근 N일 재스캔 중 채널 제약에 맞는 보정 경로를 반드시 둔다. 모든 경로는 같은 자연키로 멱등 upsert한다.

### 데이터 하한선 — 수집 개시일

**ERP가 보유한 그 채널 데이터의 시작점은 "수집을 켠 날 - 그때의 backstop 창"이다.**
그보다 이전 주문은 아무리 기다려도 자동으로는 들어오지 않는다. incremental은 당일만
보고, backstop은 최근 N일만 훑기 때문이다.

착수 시 반드시 기록하고 사용자에게 알린다.

- 수집 개시일과 그때 적용한 최초 backstop 창 → **데이터 하한선**
- 하한선 이전 주문이 업무상 필요한지(정산 대사·과거 실적·CS 조회)
- 필요하면 날짜 지정 풀스캔으로 채우되, **그 날짜의 다른 주문도 함께 유입**된다는 점을
  먼저 알린다. 과거 구간 편입은 집계·정산 기준을 바꾼다.

"과거 건이 안 보인다"는 문의를 받으면 backstop 창부터 의심하지 말고 **그 행의 최초 수집
시각과 채널 전체의 최소 주문일**을 먼저 조회한다. 창 밖인 것과 애초에 없는 것은 다르다.

## Phase 4 — 대시보드 정합성

다음 네 지점을 한 표에서 비교한다.

```text
채널 관리자 화면 ↔ 채널 API ↔ 수집 DB ↔ ERP UI
```

비교 전에 판매자, 기준시각, 타임존, 기간, 상태 정의, 주문/라인 단위를 일치시킨다. 캐시를 원인으로 단정하기 전에 이 범위를 먼저 확인한다.

- snapshot에 `asOf`와 조회기간을 저장·표시한다.
- 대시보드와 목록은 같은 수집 실행 결과를 사용한다.
- 카드 클릭은 동일 채널·기간·채널 네이티브 상태 predicate의 ERP 목록으로 이동시킨다.
- 카드 집계와 클릭 필터의 predicate를 한 계약 또는 자동 테스트로 묶어 독립 변경을
  막는다.
- 외부에서만 처리 가능한 취소·반품·교환·문의 카드는 안정적인 관리자 화면을 새 탭으로 연다.
- 탭 진입 자동수집, 수동 주문수집, 카드 새로고침은 같은 큐와 dedupe 계약을 사용한다.

## Phase 5 — 주문 처리 write

`PAID → PREPARING`은 ERP 로컬 상태 변경이 아니라 채널에 판매자 처리를 통보하는 write다.

```text
ERP 요청
  → durable queue
  → worker가 채널 원상태 재확인
  → 채널 write API
  → 요청 단위 성공/실패 기록
  → refetch
  → 채널 원천 상태를 ERP에 반영
```

- API의 accepted 응답과 실제 상태 전이를 구분한다.
- 부분 성공, 취소 경합, timeout, 429를 정상 운영 시나리오로 처리한다.
- 배치 전체가 아니라 request key별 결과를 남긴다.
- source of truth는 채널이다. ERP에서 목표 상태를 먼저 확정하지 않는다.
- 운영 write는 dry-run 결과를 보여주고 사용자 승인을 받은 뒤 1건 canary로 시작한다.

## Phase 6 — terminal reconcile

공통 정책은 다음과 같다.

1. 최근 기간 DB의 활성 주문과 채널 current list를 대사해 누락 후보를 만든다.
2. 목록 부재만으로 종결하지 않는다.
3. 단건 주문 API, 클레임 API, 웹훅 등 명시적 증거가 있는 경우에만 `CANCELLED` 또는 확인된 원상태로 갱신한다.
4. 부분 수량, 모호한 메시지, 일시적 404, 권한 오류는 기존 데이터를 보존하고 `unresolved`로 보고한다.
5. 물리 삭제하지 않는다. 기본 주문 목록에서는 `CANCELLED`를 제외하고 명시 필터에서는 감사 이력을 제공한다.
6. dry-run에서 candidate, confirmed, unresolved, error, 변경 예정 행을 출력하고 재실행 멱등성을 확인한다.

상세 취소·반품·교환 연결은 후속 확장으로 둘 수 있다. 다만 주문/라인/클레임 키, raw payload, 변경시각, 수량과 감사 이력은 지금부터 보존한다.

## Phase 7 — 큐와 실시간 UX

- 버튼은 자신이 만든 요청이 `pending` 또는 `processing`일 때만 회전한다.
- `done` 또는 `failed`에서 polling, timer, spinner를 모두 종료한다.
- 자동 refresh cooldown은 enqueue 시각이 아니라 terminal `processedAt`을 기준으로 한다.
- 완료 토스트는 큐 terminal과 화면 refetch가 끝난 뒤 표시하거나, 후속 refetch 상태를 분명히 구분한다.
- stale worker를 되살리는 reaper, 최대 retry, 오류 메시지, 중복 요청 방지를 검증한다.

“실시간”은 캐시 0초가 아니다. 명시적 새로고침과 주기 수집 뒤 기준시각이 갱신되고 채널 원천에 수렴하는 계약이다.

## Phase 8 — 검증과 배포

아래 순서를 지킨다.

1. fake 기반 adapter·normalize·queue 테스트
2. 운영 고정 IP의 read-only probe
3. DB write 없는 reconcile dry-run
4. 프로젝트 lint·typecheck·test·build
5. migration이 있으면 dry-run diff → 별도 승인 → 적용
6. 운영 write 1건 canary → 채널 화면·API·DB·ERP 네 지점 대사
7. 소량 batch → 전체 적용
8. cron/worker/log/lock/retry/reaper와 UI spinner 종료 확인

서버 배포에서는 상대경로를 보존하고 실제 런타임 import 경로를 확인한다. 파일이 복사됐다는 사실만으로 배포 성공을 판단하지 말고, 배포 대상 경로에서 compile/health check를 실행한다.

**배포 전 배포본 대조는 필수다.** 수집 서버는 레포보다 앞서 있을 수 있다(핫픽스가 서버에만
반영된 이력). 덮어쓸 파일의 해시를 교체 직전 레포 상태와 `md5`로 대조해 서버 전용 변경이
없음을 확인한 뒤에만 교체한다. 대조 없는 전체 rsync는 서버 변경을 소리 없이 롤백시킨다.
변경 파일만 배포하고 백업을 남긴다.

**마이그레이션이 있으면 브랜치를 파기 전에 원격 이력을 먼저 본다.** 운영에 이미 적용됐지만
기본 브랜치에는 없는 마이그레이션이 다른 통합 브랜치에만 있을 수 있다. 이때 잘못된 기준에서
브랜치를 따면 번호가 원격 이력보다 앞서 순서가 역전된다. `migration list`로 원격 최신
버전을 확인하고 프로젝트 브랜치 규칙에 맞는 기준에서 딴다. `db push --dry-run`이
"remote migration versions not found in local"로 막히면 그것은 마이그레이션 내용 문제가
아니라 **브랜치 기준이 틀렸다는 신호**다. 이력 조작(`migration repair`)으로 우회하지 말고
번호를 뒤로 옮기거나 브랜치를 다시 딴다.

## 완료 보고 형식

다음을 짧게 보고한다.

- 채널과 온보딩 상태(등급·발급 완료 여부·대기 중인 `[3RD]` 항목)
- 채널과 기준시각/기간
- 상태별 관리자 화면/API/DB/ERP 수와 차이
- read/write/terminal/queue의 검증 수준
- 실행한 테스트와 결과
- 배포 위치와 관측 결과
- `UNKNOWN`, unresolved, 후속 취소·반품·교환 범위
- 이번 실패에서 다음 채널 체크로 승격한 문장

완료 후 계획 이탈을 검토한다. 퀴즈를 만들거나 별도 closeout을 실행하지 않고, 간단 완료 보고, 조건부
배포 범위 선택, worktree 정리, HANDOFF, 운영배포 후 `knowns`는 최신 `dev-protocol`의 완료 절차를 따른다.

실제 운영 배포를 검증한 경우에만 `knowns`를 정확히 한 번 실행한다. 그때 관리자/API/DB/ERP 실측 증거, 승인된 상태 계약과 운영 판단, unresolved·후속 범위를 후보로 삼고 최신 `knowns` 절차를 따른다. 로컬 조사, 개발 배포, read-only reconcile에는 실행하지 않는다.

## 대표 재발 방지 패턴

| 증상 | 먼저 확인할 것 | 일반 해결 |
| --- | --- | --- |
| 키를 받았는데 첫 호출이 401/403 | 권한 활성 지연, 고정 IP 등록, 전송 방식(헤더명·스킴) | 채널 카드의 첫 호출 검증으로 판정, 활성 지연이면 대기 후 재시도 |
| API 발급 화면이 안 보이거나 막힘 | 계정 등급·사업자 인증·마스터 ID 연동 | 계정 조건을 먼저 해소, 변경 반영 시간 감안 |
| 어느 날부터 수집이 조용히 0 | 키 만료, refresh 회전분 저장 실패, 크론 장기 중단 | 만료일 모니터링, 회전 토큰 영속화, 재동의 절차 문서화 |
| 관리자 화면과 ERP 숫자가 다름 | 판매자·기간·기준시각·상태·주문/라인 단위 | 같은 scope의 snapshot과 current-state reconcile |
| 카드가 0인데 클릭하면 행이 나옴 | 카드와 목록이 같은 exact raw 상태 predicate인지 | 채널별 metric→filter 계약을 SSOT화하고 0↔0 회귀 테스트 |
| 과거 `PAID`가 계속 남음 | 생성일 증분이 상태 전이를 놓치는지 | 변경일/상태별 조회 또는 최근 기간 backstop |
| 화면에서 사라진 주문이 활성 | 단건/클레임 API의 명시적 terminal 증거 | 증거가 있을 때만 종결, 아니면 unresolved |
| 발주확인 뒤 ERP만 바뀜 | write API와 refetch 여부 | durable queue → write → source refetch |
| 완료 토스트 뒤 버튼이 계속 회전 | polling 종료 조건과 cooldown 기준 | terminal `processedAt`, done/failed에서 전체 정지 |
| 서버 코드가 엉뚱한 경로에 배포됨 | 상대경로 보존과 runtime import path | 경로 보존 배포 + 대상 경로 compile/health check |
| 자사몰 주문이 특정 마켓 주문으로 잡힘 | 그 코드가 마켓인지 **자사몰 간편구매 주문경로**인지 | `market_order_no`를 마켓 판매자센터 번호와 교차대조. 브랜드명으로 단정 금지 |
| 판매자센터엔 주문이 있는데 ERP엔 없음 | 그 마켓이 **호스팅사 경유로 이미 유입 중**인지, 다른 채널로 오귀속됐는지 | 마켓 계정 연동 목록 확인 후 기존 API 응답에서 해당 코드 실측 |
| 채널 연동됐다고 봤는데 실주문이 0 | **큐 `done`을 연동 증거로 읽지 않았는지** | 연동 판정은 판매자센터 실주문이 ERP까지 도달하는지로만 한다 |
| 과거 주문이 아무리 기다려도 안 들어옴 | backstop 창 밖인지, **수집 개시 이전**인지 | 그 행의 최초 수집 시각과 채널 최소 주문일 조회. 하한선 이전은 날짜 지정 풀스캔만이 답 |
| 동종 주문경로가 채널별로 다르게 분류됨 | 한쪽만 분리한 비대칭이 아닌지 | 같은 층위(자사몰 간편구매)는 같게 취급. 비대칭 자체가 오분류 신호 |
