# Phase 0 — 채널 온보딩

주문연동의 첫 병목은 코드가 아니라 **자격**이다. 키가 없으면 Phase 1 이후는 전부 대기다.
Phase 0의 목적은 "이 채널을 언제 붙일 수 있는가"를 착수 첫날에 확정하는 것이다.

## 원칙

1. **리드타임 있는 항목을 가장 먼저 신청한다.** 심사·계약·IP 등록·계정 권한 변경은
   사람과 제3자의 시간이다. 코드는 그동안 fake 기반으로 병렬 진행한다.
2. **행위자를 3분한다.** `[AI]` 터미널·코드·문서, `[USER]` 브라우저 로그인·동의·승인,
   `[3RD]` 고객사 담당자·채널 심사역처럼 우리가 통제하지 못하는 주체.
   `[3RD]`가 있는 항목은 착수 D-day의 종속변수다.
3. **온보딩 난이도를 먼저 분류한다.** 아래 3등급에 따라 일정 산정이 근본적으로 다르다.

   | 등급 | 의미 | 일정 특성 |
   | --- | --- | --- |
   | `SELF` | 판매자가 관리자 화면에서 즉시 발급 | 시간~하루. 코드와 동시 착수 가능 |
   | `REVIEW` | 신청 후 채널이 심사·승인 | 며칠~몇 주. 거절·부분승인 가능 |
   | `CONTRACT` | 선정·계약이 선행 | 예측 불가. 별도 사업 트랙으로 관리 |

4. **채널 카드는 착수 근거이지 보증이 아니다.** 채널 개발자센터의 화면과 정책은 자주 바뀐다.
   카드의 `확인일`이 **90일을 넘으면 공식 문서를 재확인한 뒤** 진행하고 카드를 갱신한다.
5. **근거 수준을 섞지 않는다.** `live`(실제 발급·호출로 확인) / `docs`(채널 공식 문서) /
   `3rd`(연동 솔루션사 등 제3자 가이드) / `unknown`. `3rd`는 화면 경로 힌트로만 쓰고
   비가역 결정의 근거로 삼지 않는다.

## 진입 인터뷰

사용자가 "온라인채널 주문연동 하려고 한다"고 하면, 코드를 열기 전에 다음을 한 번에 하나씩 확정한다.

1. **어떤 채널인가.** 복수면 전부. 채널마다 온보딩 등급이 다르므로 착수 순서가 갈린다.
2. **판매자 계정 상태.** 해당 채널에 판매자로 가입돼 있는가, 사업자 인증은 됐는가,
   API 발급 권한이 있는 계정을 우리가 쓸 수 있는가(계정 등급 함정이 흔하다).
3. **신청 명의.** 판매자 본인인가, 솔루션사·대행사 명의인가. 채널에 따라 요구 서류와
   승인 경로가 완전히 다르다.
4. **호출 서버.** 고정 IP가 확보돼 있는가, 아직 미프로비저닝인가. IP 화이트리스트
   채널은 서버가 정해지기 전엔 키가 무용하다. 서버 이전 시 재등록도 미리 계산한다.
5. **이번 범위.** read 수집만인가, 발주확인 같은 write까지인가, 클레임·정산·문의까지인가.
   write는 권한 스코프와 심사 범위를 키운다.

## 산출: 착수 브리프

인터뷰 뒤 다음 3블록을 **이 순서로** 제시한다. 순서가 곧 우선순위다.

```text
A. 지금 당장 신청해야 할 것   [USER]/[3RD] 리드타임 항목, 예상 소요와 함께
B. AI가 병렬로 진행할 것      문서조사·어댑터 스켈레톤·fake 테스트·매핑 초안
C. 키 도착 후 착수            Phase 1~8 (live probe → dry-run → canary)
```

A가 비어 있는 채널은 그날 Phase 1로 넘어가고, A에 `CONTRACT`가 있는 채널은
**폴백(수동 인제스트 등)을 함께 제시**한다. 승인만 기다리며 범위를 비워두지 않는다.

## 온보딩 카드 스키마

`references/channels/<channel>.md`는 다음 12절을 따른다. 빈 절은 지우지 말고
`미확인`으로 남겨 조사 부채를 드러낸다.

| 절 | 내용 | 왜 필요한가 |
| --- | --- | --- |
| 0 헤더 | 채널명·내부코드·온보딩 등급·확인일·출처 | stale 판정과 근거 추적 |
| 1 선행조건 | 판매자 가입, 사업자 인증, 계정 등급·권한, 마스터 ID 연동 | 대부분의 발급 실패가 여기서 난다 |
| 2 신청 경로 | 진입 URL과 화면 클릭 경로 | 사용자가 헤매지 않게 |
| 3 심사·리드타임 | 심사 유무, 제출물, 소요, 부분승인·거절 가능성 | 일정 산정의 핵심 |
| 4 발급 결과물 | 받는 키의 종류와 수령 방법 | env 설계와 보관 위치 |
| 5 키 수명·회전 | 만료·갱신·회전 규칙 | 운영 중 무증상 수집중단의 주범 |
| 6 네트워크 요건 | 고정 IP 등록 여부, 등록 개수 제한, 이전 시 절차 | 서버 프로비저닝 선후관계 |
| 7 권한·스코프 | 권한 단위와 read/write 구분 | 범위 확대 시 재신청 여부 |
| 8 역할 분담 | `[AI]`/`[USER]`/`[3RD]` 단계별 | 대기의 주체를 명확히 |
| 9 첫 호출 검증 | 키가 살아있는지 확인하는 최소 read | 발급 직후 즉시 판정 |
| 10 함정 | 이 채널 특유의 실패 | 재발 방지 |
| 11 폴백 | 승인 지연·거절 시 대안 | 프로젝트를 멈추지 않기 위해 |

## 자격증명 취급

- 값은 저장소·문서·이슈에 절대 남기지 않는다. **보관 위치만** 기록한다(고객사 소유 secret manager의 식별자, 고객사 서버 경로).
- 회전형 토큰(refresh 회전 등)은 저장 실패가 곧 lock-out이다. 영속화 코드를 먼저 만들고 발급한다.
- 만료가 있는 키(1년·180일 등)는 발급 즉시 **만료일을 운영 캘린더·모니터링에 등록**한다.
  만료 사고는 조용히 수집이 0이 되는 형태로 나타난다.
