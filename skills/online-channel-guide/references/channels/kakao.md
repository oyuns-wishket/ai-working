# 카카오톡스토어 / 카카오쇼핑 — 온보딩 카드

| 항목 | 값 |
| --- | --- |
| 내부코드 | `kakao` |
| 온보딩 등급 | **`SELF`**(카페24 마켓플러스 경유) / **`CONTRACT`**(카카오쇼핑 직접 API) |
| 확인일 | 2026-08-06 |
| 출처 | 카페24 마켓플러스 지원 마켓 목록, Admin API와 판매자센터의 교차 검증 절차 |

> ⚠️ **2026-08-06 정정**: 이 카드는 이전에 "일반 판매자에게 미개방(`CONTRACT`)"으로만
> 기술했다. 그 서술은 **직접 API에만 해당**했고, 실전 경로인 **카페24 마켓플러스 경유**를
> 누락하면 "톡스토어는 사실상 연동 불가"라는 오판을 낳는다. 마켓플러스로 이미 연결된 몰은
> 주문이 Admin API에 들어올 수 있다.

## 0. 먼저 확인할 것 — 이미 들어오고 있을 수 있다

카카오톡스토어는 **자사몰 호스팅사(카페24)의 마켓플러스가 공식 지원**한다. 직접 API 없이도
주문이 이미 유입 중일 수 있으므로 온보딩을 시작하기 전에 다음을 본다.

1. 카페24 어드민 `기본 > 계정관리 > 마켓계정관리`에 **카카오톡 스토어 계정이 등록**돼 있는가.
   (판매자 ID, 카카오계정, `store.kakao.com/<도메인>`, API 인증키를 입력하는 화면)
2. 등록돼 있으면 **이미 쓰고 있는 카페24 Admin API `GET /admin/orders` 응답에 섞여 들어온다.**
3. 그렇다면 필요한 작업은 신규 온보딩이 아니라 **채널 귀속 분류**뿐이다.

## 1. 두 경로 비교

| | 카페24 마켓플러스 경유 | 카카오쇼핑 직접 API |
| --- | --- | --- |
| 등급 | `SELF` | `CONTRACT` |
| 선행조건 | 카페24 쇼핑몰 + 톡스토어 판매자 | 카카오의 **선정 + 계약** |
| 고정 IP | 불필요(카페24 OAuth) | 미확인 |
| 리드타임 | 계정 연동 즉시 | 예측 불가(사업 트랙) |
| 주문 read | ✅ Admin API에 함께 유입 | 계약 후 |
| 송장/상태 write | 카페24 계약 범위를 따름 | 계약 후 |
| 권장 | **기본 경로** | 볼륨이 크고 마켓플러스로 부족할 때만 |

직접 API는 카카오쇼핑 Open API(`shopping-developers.kakao.com`)의 「카카오쇼핑 API 연동
검토 요청하기」 신청서 제출 → 개별 메일 회신 → 계약 체결 순이며, 대상은 주로 대형제휴사·
브랜드·대행사·호스팅사다. 소요 기간은 문서에 없다. 기술 트랙이 아니라 **사업 트랙**으로
관리하고 프로젝트 크리티컬 패스에 넣지 않는다.

## 2. 마켓플러스 경유 — 검증할 계약

카페24 Admin API 주문 응답에서 톡스토어 주문은 다음으로 식별한다.

| 필드 | 값 |
| --- | --- |
| `market_id` / `order_place_id` | `kakao` |
| `order_place_name` | `카카오톡 스토어` |
| `market_order_no` | **톡스토어 판매자센터 결제번호(10자리)** |
| `order_id` | 카페24 형식(`YYYYMMDD-NNNNNNN`) — 마켓 주문도 카페24 주문번호를 받는다 |

### ⚠️ 톡체크아웃(`KAKAOPAY`)과 혼동 금지 — 실제 사고 지점

| 코드 | 표시명 | 정체 | 정본 채널 |
| --- | --- | --- | --- |
| `kakao` | 카카오톡 스토어 | **마켓 주문** | `kakao` |
| `KAKAOPAY` | 톡체크아웃 | **자사몰** 상품페이지·장바구니의 카카오 간편구매 | `cafe24` |

톡체크아웃은 주문서가 카페24에 생성되고 카페24 주문관리에서 처리된다. 결제수단도
card/prepaid/cash로 흩어져 있어 결제 기준도 아니다. **네이버페이 주문형(`NCHECKOUT`)과
같은 층위**이므로 자사몰로 둔다.

둘을 뒤바꾸면 자사몰 주문은 마켓 채널로, 실제 톡스토어 주문은 자사몰로 잘못 귀속된다.
해소 근거는 **판매자센터 결제번호 ↔ `market_order_no` 교차대조**여야 한다.

분류 상수는 정확히 이렇게 둔다(대소문자 정규화 후 정확 일치, 부분일치·prefix 금지 —
`KAKAO`와 `KAKAOPAY`가 갈라져야 한다).

## 3. 상태 매핑

마켓플러스 경유 주문은 **카페24 주문상태 체계를 그대로 따른다**(`N10`/`N20`/`N30`/`N40`,
`C4x` 취소, `R` 반품, `E` 교환). 별도 카카오 상태 enum을 만들지 않는다. 카페24 카드의
상태 매핑을 재사용한다.

톡스토어 판매자센터 자체 상태(`601 구매 결정`, `507 반품 결제 취소 완료` 등)는 참고용이며,
ERP 정규화는 카페24 원상태를 정본으로 한다.

## 4. 역할 분담

| 주체 | 할 일 |
| --- | --- |
| `[USER]` | 카페24 마켓계정관리에 톡스토어 계정 연동(카카오계정·비밀번호·도메인·API 인증키 입력, 인증하기) |
| `[AI]` | 연동 후 Admin API 실측으로 `market_id` 확정, 귀속 분류·회귀 테스트, 판매자센터 교차대조 |
| `[3RD]` | (직접 API를 갈 때만) 카카오의 선정·계약 |

## 5. 첫 호출 검증

별도 인증 없이 **기존 카페24 토큰으로** 검증한다.

1. 톡스토어 판매자센터에서 최근 주문 몇 건의 **주문일·결제번호·금액**을 확보한다.
2. 그 주문일로 `GET /admin/orders`를 read-only 조회한다.
3. 응답에서 `market_id`별 분포를 집계하고, `market_order_no`가 판매자센터 결제번호와
   **정확히 일치하는 행**을 찾는다.
4. 일치하면 그 `market_id` 값이 이 몰의 톡스토어 코드다. 추측하지 말고 이 값만 매핑한다.

## 6. 함정

- **직접 API 등급(`CONTRACT`)만 보고 "연동 불가"로 판단하지 않는다.** 호스팅사 경유가
  실전 경로다. 이 카드의 이전 버전이 정확히 그 오판을 유발했다.
- **`KAKAOPAY`를 톡스토어로 매핑하지 않는다.** 브랜드명이 코드에 들어갔을 뿐 자사몰이다.
- **표시명으로 분류하지 않는다.** `order_place_name`은 지역화·가변 문자열이다.
- **큐가 `done`으로 끝나는 것을 연동 증거로 읽지 않는다.** 그것은 카페24 수집 경로가
  돌았다는 뜻일 뿐이다. 연동은 판매자센터 실주문이 ERP까지 도달하는지로 판정한다.
- 「선물하기」와 「톡스토어」는 서비스가 다르다. 어느 쪽 주문인지 먼저 확정한다.
- 톡스토어는 볼륨이 작을 수 있다. 표본이 적어 상태 enum을 전수
  관측하기 어려우므로 미관측 값은 `UNKNOWN`으로 보존한다.
- 데이터 하한선 주의 — 카페24 수집 개시 이전의 톡스토어 주문은 ERP에 없다. 과거분이
  필요하면 날짜 지정 풀스캔이 유일한 경로이며, 그 날짜의 자사몰 주문도 함께 유입된다.

## 7. 폴백

마켓플러스 연동이 불가하거나 볼륨이 극히 작으면 톡스토어 판매자센터 주문 엑셀의
수동/반자동 인제스트로 업무를 돌린다. 직접 API(`CONTRACT`)는 볼륨이 이를 정당화할 때만
사업 트랙으로 추진한다.
