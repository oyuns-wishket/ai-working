# 네이버 스마트스토어 (커머스 API) — 온보딩 카드

| 항목 | 값 |
| --- | --- |
| 내부코드 | `naver` |
| 온보딩 등급 | `SELF` (단, 계정 등급 조건을 못 넘으면 발급 불가) |
| 확인일 | 2026-07-31 |
| 출처 | 네이버 커머스API센터 `apicenter.commerce.naver.com/docs`, 연동 솔루션사 가이드 |

## 1. 선행조건

- 스마트스토어 판매자 계정.
- ⚠️ **커머스API센터는 「통합매니저」 계정으로 로그인해야 한다. 일반 매니저 계정으로는
  API 발급이 불가능하다.** 권한 변경이 필요하면 스마트스토어센터에서 먼저 바꾸고,
  변경 반영에 약 1~2시간이 걸린다. `3rd`

## 2. 신청 경로

커머스API센터 → `계정생성` → 스마트스토어 전용 커머스 API 선택 → 로그인 →
개발업체 계정명·**장애대응 연락처** 입력 → 가입 → `애플리케이션 등록` → `등록하기` →
애플리케이션 이름·설명·**API 호출 IP** 입력 → **API 그룹 권한** 선택(문의/상품/주문/판매자정보 등)
→ 등록 → 화면에서 **애플리케이션 ID·시크릿** 확인. `3rd`

## 3. 심사·리드타임

별도 심사 없음. 계정 등급이 맞으면 당일 발급. 권한 변경이 선행되면 1~2시간. `3rd`

## 4. 발급 결과물

`client_id`(애플리케이션 ID), `client_secret`(애플리케이션 시크릿). `live`

## 5. 키 수명·회전

- 액세스 토큰은 매 호출 전 발급받는 구조. 유효 `10,800초`, 만료 60초 전 갱신이 안전. `live`
- ⚠️ **서명식이 특이하다**: `client_secret_sign = base64(bcrypt.hashpw(f"{client_id}_{timestamp}", client_secret))`
  — **client_secret이 bcrypt salt로 쓰인다**. `timestamp`는 ms epoch이며 서버시계보다
  살짝 과거(now-3s)로 보내야 안전하고, 5분간 유효하다. `live`
- `grant_type=client_credentials`, `type=SELF`. `live`

## 6. 네트워크 요건

- **고정 IP 등록 필수.** 애플리케이션 등록 화면에서 **최대 3개**까지. `3rd` / `live`
- 서버 이전(예: 클라우드 이전) 시 새 IP 재등록이 선행돼야 한다. 실제로 IP 등록 대기 때문에
  구현이 offline-only 상태로 멈춘 사례가 있다. `live`

## 7. 권한·스코프

등록 시 **API 그룹 단위**로 선택한다(문의·상품·주문·판매자정보 등). 범위를 넓히려면
애플리케이션 설정에서 그룹을 추가한다. `3rd`

## 8. 역할 분담

| 주체 | 할 일 |
| --- | --- |
| `[USER]` | 통합매니저 권한 확인·변경, 커머스API센터 가입, 애플리케이션 등록, IP 입력 |
| `[AI]` | bcrypt 서명 구현, 2단계 조회 어댑터, fake 테스트, 발급 후 probe |
| `[3RD]` | 고객사 소유 계정이면 담당자의 권한 변경·IP 등록 (대기 항목) |

## 9. 첫 호출 검증

토큰 발급 → 변경상품주문 조회(`last-changed-statuses`)를 24시간 이하 창으로 1회.
`401 GW.AUTHN`이면 서명·시계, IP 등록을 먼저 본다.

## 10. 함정

- 날짜 파라미터는 KST ISO 오프셋 포함(`2026-07-11T00:00:00.000+09:00`)이고,
  **쿼리스트링에서 `+`는 반드시 `%2B`로 인코딩**해야 한다. `live`
- 변경일 조회 창은 **≤24시간**, 응답 최대 300. 페이징 커서는 top-level이 아니라
  **`data.more.moreFrom` + `data.more.moreSequence`를 함께** 전진시켜야 한다.
  이걸 놓치면 한 창 300건 초과분이 조용히 누락된다. `docs`
- 상세 조회는 상품주문번호 ≤100~300건/콜. `docs`
- 발주확인은 `productOrderStatus`를 바꾸는 게 아니라 **별도 필드 `placeOrderStatus`**가
  `NOT_YET → OK`로 바뀐다. 화면 문구만 보고 다른 채널과 같다고 가정하지 않는다. `live`
- 발주확인 응답은 HTTP 200 안에 `successProductOrderInfos`/`failProductOrderInfos`가
  함께 온다. **배치 200을 요청 단위 성공으로 간주하면 안 된다.** `live`
- 클레임은 `claimType`만으로 세면 안 된다. `EXCHANGE_REDELIVERING`(재배송중)은
  `교환요청`이 아니다. 카드와 목록이 같은 exact `claimStatus`를 써야 한다. `live`
- 상태는 주문이 아니라 **상품주문(item) 레벨**이다. `live`

## 11. 폴백

스마트스토어센터 주문 엑셀 수동 인제스트. (주문양식이 암호화 배포되는 경우가 있어
비밀번호 확보가 선행될 수 있다.)
