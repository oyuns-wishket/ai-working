# AI가 모델 제작부터 웹 연동까지 맡는 3D 작업

3D 랜딩·상품 체험 요청에서 모델 자산이 없거나 수정이 필요할 때 읽는다. 영상·입자·게임 같은 연출은 먼저 [graphics-production.md](graphics-production.md)로 모델이 필요한지와 전달 경로를 판단한다. 사용자는 표현 의도·취향·실물 유사도를 판단하고, 에이전트는 자산 탐색·제작·수정·최적화·export·웹 구현을 수행한다. “Blender를 배워서 모델을 만들어 오세요”로 기술 작업을 넘기지 않는다.

[tool-capabilities.md](tool-capabilities.md)로 서비스별 사용 가능 기능을 확인한다. 웹 runtime·스크롤·접근성·성능은 [motion-and-3d.md](motion-and-3d.md), 도구 준비는 [tooling.md](tooling.md)를 따른다. 게이트·도구 기본값·규칙 소유는 [SKILL.md](../SKILL.md)를 따른다. 이 문서는 모델 확보·제작·편집·export와 자산 검수 상세를 소유한다. 모션 도구·timing은 [motion-design.md](motion-design.md)를 따르며 별도 인터뷰·방향·시안 게이트를 추가하지 않는다.

## 1. 짧은 요구를 제작 조건으로 바꾸기

기존 답변을 먼저 사용하고, 결과를 바꾸는 미확정 항목만 쉬운 말로 묻는다.

- 대상: 실제 판매 제품, 가상의 오브젝트, 캐릭터, 공간 중 무엇인가?
- 외형: “사진 같은 실물”, “깔끔한 제품 렌더”, “장난감 같은 스타일” 중 어떤 방향인가?
- 변화: 회전·확대, 뚜껑 열림, 부품 분해, 형태 변형 중 무엇을 보여주는가?
- 사용: 스크롤 이야기, 자유 회전, 색/옵션 선택 중 어떤 조작이 필요한가?
- 운영: 기존 stack, 모바일 대상, 직접 호스팅 요구, 이미 제공된 파일·사진을 확인한다.

실물과 일치해야 하는 경우 원본 CAD/모델·제품 사진·치수 중 필요한 최소 자료를 요청한다. 자료가 없는 부분을 추정한 초안은 표시하고 정확한 제품 모델이라고 보고하지 않는다. 엔지니어링 수치나 3D 전문 용어 선택을 사용자에게 맡기지 않는다.

## 2. 완성 자산을 만들 수 있는 경로 선택

| 조건 | 에이전트 실행 경로 | 실패 시 다음 경로 |
|---|---|---|
| 무료·로컬·장기 수정/자체 호스팅 필요 | 권리 확인한 모델/재질 확보 → Blender 편집 → 원본 `.blend`와 GLB → 기존 웹 stack | 적합한 권리/구조의 자산이 없으면 로컬 제작 초안을 검수한다. 실제 제품 정확도가 부족하면 필요한 원본을 특정하고 그 부분은 미완료로 남긴다. |
| 새 추상/스타일화 형태, 적절한 자산 없음 | 승인된 콘셉트에 맞춰 Blender Python/API로 모델·재질·조명 제작 → 시각 피드백 반복 → export | silhouette·재질·export 결함이면 같은 원본을 수정한다. 현재 도구로 불가능하면 권리 확인한 자산 또는 허용된 생성 서비스와 표현 차이를 비교한다. |
| Spline의 필요한 기능과 연결 사용 가능 | 기존 씬/Library 또는 AI 생성 → 공식 Desktop MCP/사용 가능한 편집 도구로 수정 → 지원 export로 웹 연동 | 연결/권한 실패이면 tool-capabilities의 분기를 따른다. GLB로 요구를 보존할 수 있으면 Blender 경로를 검증하고, 이벤트·호스팅이 달라지면 차이를 보여주고 결정받는다. |
| 생성 서비스가 필요한 형태에 적합 | Meshy/Tripo 등의 허용된 생성 → 다운로드 검수 → Blender에서 구조·재질 정리 → GLB | 같은 방식이 연속 두 번 실패하면 재생성을 멈추고 자산/제작 경로를 재평가한다. 부품·정확도 결함이면 Blender 수정 또는 원본 기반 제작으로 전환한다. |
| 정밀 제품·복잡한 변형을 현재 도구로 재현하기 어려움 | 준비한 초안/차이와 필요한 원본 또는 전문 제작 범위를 보여주고 다음 경로 결정 | 원본 기반 수정/전문 제작 범위를 구체화한다. 영상·단계 설명으로 바꾸면 핵심 조작이 달라지는지 보여주고 결정받는다. 대체 결정을 받기 전 정확도·조작을 낮추지 않는다. |

Three.js/R3F는 renderer이며 전문 모델을 공급하지 않는다. 기본 도형 조합은 의도된 추상 디자인이나 표시된 placeholder에 사용한다. 전문 도구를 호출했다는 사실만으로 형상 완성도가 보장되지는 않는다.

무료 경로도 실제 산출물을 만드는 경로여야 한다. 예를 들어 상업 사용 가능한 [Poly Haven 모델·재질](https://polyhaven.com/license)을 에이전트가 탐색·다운로드하고 Blender에서 수정한다. 적합한 무료 자산이 없으면 제작 가능한 초안을 먼저 보여준다. 승인된 실물 정확도나 독립 호스팅을 조용히 낮추지 않는다.

## 공식 예제 관찰과 채택 기록

1. 새 방향이면 과업에 맞는 공식 실행 예제를 찾아 브라우저에서 직접 조작한다. 제작 도구의 예제 원본이면 해당 도구에서 열어 재생·회전하고, 웹 전달 후보도 브라우저에서 확인한다. 제작 도구 안에서의 검수만으로 웹 공식 예제 관찰 완료를 기록하지 않는다. 완료 조건은 [SKILL.md의 공통 원칙](../SKILL.md#공통-원칙)을 따른다.
2. **예제 URL → 직접 조작한 행동 → 관찰 결과 → 이번 시안에 채택할 표현 → 접근 불가 시 대체 근거와 한계** 순서로 기록한다. 공식 예제와 제작자 사례를 구분하고, 관찰한 표현만 채택 근거로 쓴다.
3. 직접 관찰이 미완료이면 새 방향의 최종 채택과 application source 구현을 보류한다. 접근 가능한 실행본이 있으면 결정을 묻지 않고 직접 조작한다. 접근 불가(URL 응답 실패·로컬 실행 실패의 실제 근거)가 확인된 경우에만 사용자에게 접근 가능한 공식 실행본 확보·공식 소스의 로컬 실행·해당 방향 보류 중 하나를 결정받는다. 대체 자료와 진행 요청은 직접 관찰 완료를 대신하지 않는다.
4. 승인된 패턴의 작은 수정이면 기존 관찰·선택 근거를 링크하고 변경한 상태를 대조한다. 새 표현이면 아래 시안 선택을 수행한다. `small-feature`는 대상 구간만 좁히고 조사·시안(새 표현일 때)·검증의 강도를 유지한다.
5. 접근 실패이면 실제 시도한 URL·로컬 실행 명령과 오류, 실제 확인한 공식 영상·문서·소스, 확인하지 못한 입력·성능을 아래 표에 적는다. 문서 읽기·설치·외부 링크 제공·자체 제작 시안을 공식 예제의 직접 동작 관찰로 기록하지 않는다. 준비를 계속하면 분리된 preview 경로만 사용하고 미관찰 방향은 미확정으로 표시한다.
6. 기록은 기존 DESIGN/구현노트의 해당 결정에 연결한다. 기록 없는 기존 패턴의 재사용은 [SKILL.md의 공통 원칙](../SKILL.md#공통-원칙)으로 판정하고, 새 표현이 아니면 `기존 코드 패턴 재사용(미승인)`으로 표시해 원 코드·동작 동일성·새 표현 아님 판정 근거·변경 상태 검증을 연결한다. `small-feature`의 범위 가드와 검증 강도는 그대로 유지한다. `audit`이면 이 절 전체를 읽기 전용 조사에만 적용하고 로컬 실행본 준비·시안·기록 파일 생성·설치를 하지 않는다.

| 예제 URL | 직접 조작한 행동 | 관찰 결과 | 이번 시안에 채택할 표현 | 접근 불가 시 대체 근거와 한계 |
|---|---|---|---|---|
| 실제 URL·관찰일·공식/제작자 구분 | 입력·시작 상태·왕복/초기화 등 실행한 행동 | 시작/전환/완료의 관찰과 증거 위치 | 대상 구간·채택할 상태 연결/표현 | 접근 성공이면 해당 없음; 실패이면 시도 URL/명령·오류·실제 대체 자료·미확인 항목·확보/로컬 실행/보류 결정 |

이 표는 [verification.md](verification.md)의 공통 관찰 표에 연결하는 상세 자료다. 예제 URL·행동·관찰·채택은 공통 표의 같은 항목에 대응하고, 대체 근거/한계는 URL·관찰에 함께 남긴다. 대조 결과는 아래 실제 검증 결과를 연결해 갱신한다. 같은 증거를 별도 문서에 중복 작성하지 않는다.

## 3. 콘셉트 → 입체 검수 → 수정

콘셉트·입체 검수는 [SKILL.md](../SKILL.md)의 3단계(시각 방향) 선택 뒤 준비하고 4단계 세 시안 안에서 함께 제시한다. 피드백·반복 수정은 시안 결정의 `수정` 처리이며 별도 승인 라운드가 아니다. 수정한 시안의 재제시·승인은 SKILL.md의 부분 승인과 재제시 규칙을 따른다. scoped 작업이면 신규 전용 3·4단계를 다시 시작하지 않고 해당 구간의 동작 시안에 통합한다.

3D scroll 장면의 시안에는 실제 scroll/interaction 미리보기와 replay를 반드시 포함한다. 정지 다각도 렌더만으로는 시안 게이트를 통과할 수 없다.

새 그래픽·3D 방향의 동작 시안 세 개에는 [graphics-production.md의 동작 시안 기준](graphics-production.md#3-ai-제작--시안--웹-전달)을 적용한다. 세 안은 장면 구조(카메라 경로·구간 순서)·조작/반응 방식·전달 경로 중 최소 두 가지에서 달라야 하며 색·조명 강도·easing만 바꾼 안은 부적합이다. 같은 콘텐츠·대표 행동과 승인된 범위 안에서 비교하며, 세 안의 각 쌍(A/B·A/C·B/C)에 이 기준을 적용한다.

새 차트·모션·그래픽·3D 방향을 제작할 때는 해당 소유 참조의 **공식 실행 예제 직접 관찰 → 채택할 표현 지정 → 같은 데이터/콘텐츠로 동작 시안 정확히 세 개 → 결과 대조**를 따른다. 정지 이미지·외부 링크만으로 대체하지 않는다. 모션·차트·그래픽·3D가 들어가는 동적 시안은 **실제 동작**(재생/초기화, 클릭·필터·스크롤 조작)을 반드시 포함한다. [SKILL.md](../SKILL.md)의 선택된 시각 방향 안에서 모델 후보와 조명/구도를 준비한다. 신규 작업의 세 composition에 자산 검수와 동작을 함께 넣고, 모델·재질·모션마다 별도 세 방향/세 시안 게이트를 연속해서 만들지 않는다. 승인 전 제작·렌더·기술 검증은 분리된 preview 경로에서 한다.

1. **콘셉트**: 사용할 모델 후보 또는 제작할 형태, 재질, 카메라, 스크롤 장면을 이미지와 짧은 설명으로 보여준다. AI 이미지 콘셉트와 실제 3D 모델을 구분한다.
2. **입체 검수**: 정면·옆·뒤·대표 각도와 간단한 회전을 렌더한다. 형태 판단이 필요하면 재질을 뺀 clay view와 mesh 상태도 에이전트가 확인한다. 예쁜 정면 텍스처로 뒤쪽 결함을 가리지 않는다.
3. **쉬운 피드백**: “더 둥글게”, “금속 느낌을 약하게”, “뒤쪽이 어색해”, “제품이 더 크게”를 받아 에이전트가 geometry·roughness·조명·카메라 변경으로 번역한다.
4. **반복 수정**: 원본을 보존하고 지적된 부분을 수정한 뒤 같은 각도/조명에서 전후 비교를 보여준다. 대상만 회전/이동할지 형태 자체를 바꿀지 구분한다.
5. **확정**: 실제 사용할 자산을 선택된 composition에 배치하고 필요한 동작·모바일 대안을 확인한다. 승인된 placeholder가 실물 자산의 완성 승인을 뜻하지는 않는다.

사용자에게는 결과와 바뀐 점을 보여준다. mesh 정리·UV·pivot·export 설정·웹 연결은 에이전트가 처리한다. 시안 URL은 메인 스킬의 로컬 서버 규칙을 따른다.

## 4. 실제 제작·내보내기

### Blender 경로

- 현재 환경에서 Blender 실행 파일과 버전을 확인한다. 사용할 수 있는 공식 Python/API 또는 검토한 MCP로 기존 파일을 열고 작업한다. 없는 도구의 설치/연결은 허용된 환경 설정 범위에서 에이전트가 수행한다.
- 에이전트가 실행할 작업 스크립트를 분리된 작업 경로에 작성한다. import → 단위/축 정리 → 부품 이름·pivot → 재질/조명 → 대표 뷰 렌더 → 원본 저장 → GLB export를 이번 요구에 맞게 수행한다. headless 작업은 확인된 실행 파일로 `--background --python`을 실행한다.
- 생성 형상과 외부 모델 모두 silhouette, normals, mesh 분리, UV/texture, 불필요한 내부 geometry를 검수한다. 고해상도 원본과 웹용 자산을 구분한다.
- 분해에는 분리된 부품, 관절에는 rig/clip, 형태 변형에는 호환되는 shape keys/morph 데이터가 필요하다. 임의의 두 생성 모델을 자동으로 morph 가능하다고 취급하지 않는다.
- exporter가 지원하는 PBR 재질·변형으로 정리하고 필요한 bake를 수행한다. Blender 화면의 임의 shader·modifier·물리 효과가 GLB에 모두 보존되는 것은 아니다. [공식 glTF export](https://docs.blender.org/manual/en/5.0/addons/import_export/scene_gltf2.html)
- `.blend`와 GLB를 실제 저장하고 다시 로드해 부품·재질·animation을 검사한다. 웹에서 표현할 조명과 카메라는 최종 renderer에서 다시 확인한다.

### Spline 및 생성 서비스 경로

- Spline은 기존 씬/무료 Library/허용된 AI 생성을 활용한다. 공식 Desktop MCP가 연결돼 있으면 에이전트가 scene/object 검사·편집·카메라·screenshot을 수행한다. Desktop 앱이 필요하고 클라우드 AI 생성은 로컬 MCP 연결과 별개다. [MCP](https://docs.spline.design/generate/spline-mcp-server), [Library](https://docs.spline.design/designing-in-3-d/scenes/3d-library), [AI 생성](https://docs.spline.design/generate/ai-3d-generation)
- 연결이 안 되면 에이전트가 해결 가능한 설정부터 처리한다. 직접 할 수 없는 로그인·GUI 동작만 정확한 클릭 경로로 짧게 요청하고, 완료 후 에이전트가 제작을 재개한다. 전체 모델링·export를 사용자에게 넘기지 않는다.
- Spline runtime을 유지하는 export와 GLB 이식 경로를 구분한다. GLB는 Spline의 상태/이벤트·조명·후처리를 모두 담지 않는다. 모델만 GLB로 쓰면 웹 연출을 별도로 구현한다. 자체 파일 호스팅과 runtime까지 독립적인 self-host도 구분한다. [GLB 제약](https://docs.spline.design/exporting-your-scene/files/exporting-as-gtlf-glb), [self-host](https://docs.spline.design/exporting-your-scene/web/exporting-as-self-hosted-project)
- Meshy/Tripo 결과는 다운로드·상업 사용·수정 조건을 확인한 뒤 실제 파일을 검수한다. 생성 서비스 미리보기만 보고 제작 완료로 표시하지 않는다. 부품 구조·정확한 치수·변형 가능 여부는 에이전트가 확인한다.
- 연결·쿼터 문제에는 [기능 선택 분기](tool-capabilities.md)를 적용한다. 입력을 다른 서비스로 보내야 하는 무료 대체도 기존 외부 전송 범위 안에 있어야 한다.

## 5. 웹 연동과 납품

application source 잠금 해제 후 선택한 asset을 로컬 프로젝트에 반영하고 기존 stack에 연결한다. React에서는 R3F/Drei, 그 외에는 Three.js 또는 선택한 viewer 등 실제 호환 경로를 사용한다. 스크롤 진행률·카메라·animation clip에는 각각 하나의 제어 주체를 둔다.

HTML 설명·CTA를 모델 로딩보다 먼저 사용할 수 있게 하고, 모바일 구도·reduced motion·로드 실패 대안을 구현한다. 실물 재질, 시작/중간/끝 전환, 역방향 scroll, 새로고침 복원, route 재진입을 최종 웹에서 검사한다. 성능 조건과 실측은 [motion-and-3d.md](motion-and-3d.md)를 따른다.

산출물은 기존 프로젝트 구조에 맞춰 남긴다. 원본이나 라이선스가 저장소 배포를 허용하지 않으면 승인된 asset 저장소를 사용한다.

- 편집 가능한 원본: Blender 경로의 `.blend`, 또는 사용 가능한 Spline 원본/편집 프로젝트와 접근 인계 방식.
- 웹 납품 파일: 검증된 GLB·텍스처 또는 선택한 씬 export. Spline 씬과 부가 GLB의 표현 차이가 있으면 기록.
- 출처/라이선스·원본 대비 가공 내용·part/clip 이름·단위·재현 가능한 작업 스크립트.
- 실제 모델의 대표 각도, 선택한 모션/모바일 fallback, 검증 URL과 결과를 [DESIGN](../assets/DESIGN.template.md)에 연결.

예: “화장품 병이 스크롤하면 열리게” → 실물 자료와 뚜껑/몸체 확인 → 에이전트가 모델 확보·분리·재질 수정 → 열림 시안 → GLB와 웹 연동. “무료로 귀여운 캐릭터 랜딩” → 권리 확인한 자산 또는 에이전트 제작 → 다각도 피드백 → 웹용 최적화. “Spline 구독 중인데 직접 호스팅” → 필요한 export 권한 확인 → 가능한 완전 self-host 또는 준비한 GLB 대안의 표현 차이를 보고 결정.

## 6. 자산 검수와 최종 웹 대조

[verification.md](verification.md)는 공통 실행 순서·증거 형식과 목적별 검증 요약을 소유하고, 이 절은 모델 제작·export 검수의 상세를 소유한다. 3D runtime·scroll·자산 최적화·성능 검증은 [motion-and-3d.md](motion-and-3d.md), 모션 상태와 reduced motion 설정 변경은 [motion-design.md](motion-design.md)를 함께 적용한다.

1. 선택된 모델 원본과 실제 export를 다시 연다. silhouette·앞/옆/뒤·대표 각도·부품 이름/계층·단위/축·pivot·재질/texture·clip·변형 데이터를 대조한다. 원본 없이 생성 결과만 있으면 편집 가능 범위와 부족한 자료를 명시한다.
2. 분해가 요구되면 각 부품이 올바른 pivot과 기준 위치에서 분리·복귀하는지 검사한다. 형태 변형이면 실제 export의 지원 데이터를 재생한다. 부품이 하나뿐이거나 동작 데이터가 없으면 해당 조작 준비가 실패한 것이다.
3. 원본과 최적화된 자산을 같은 카메라·조명·포즈에서 비교한다. byte 감소와 geometry/draw-call 감소를 구분하고 최적화 후 잃은 부품·morph·clip이 없는지 확인한다. loader/decoder/texture 요청 성공은 실제 웹에서 확인한다.
4. 승인된 동작 시안과 실제 웹을 같은 route·viewport·data/state·theme·auth·모델·대표 행동에서 대조한다. 클릭/scroll 왕복·여러 각도·재생/초기화와 모바일·느린/실패한 로드·reduced motion을 실행한다. 시안의 대체 모델 승인을 실제 제품 형상·재질의 정확성 승인으로 기록하지 않는다.
5. 정확한 제품이면 제공 원본/치수 또는 실제 사용자 확인과 대조한다. 원본·사진으로 확인하지 못한 뒷면이나 내부는 추정으로 표시한다. 영상/렌더의 외관 통과와 치수·구조 정확성 통과를 구분한다.
6. 편집 원본·재현 스크립트·웹 자산·라이선스/출처·납품 위치와 실제 검증 URL을 연결한다. export 실패·필수 부품 누락·웹 통합 미완료이면 위 실패 시 다음 경로로 이어가고 미해결 범위를 남긴다. 모델 생성·다운로드만으로 웹 제작 완료를 보고하지 않는다.

아래 상세 표는 [verification.md](verification.md)의 공통 검증 표 `결과`에 증거로 연결한다. 공통 표의 명령/route·조건·통과/실패/미실행/N/A·미실행 사유를 대체하지 않는다.

| 자산/단계 | 비교 조건·기대 계약 | 실제 검사·증거 | 판정 | 수정/대체 경로·미확인 한계 |
|---|---|---|---|---|
| 원본 → export → 최적화 → 웹 | 같은 각도/조명/포즈·부품·재질·clip·대표 행동 | 파일·다각도 렌더·직접 조작 기록·실측 링크 | 반영 / 조정 / 누락 / 미실행 | 실제 제품 정확도 근거·재검증·잔여 범위 |

모델 검수도 `small-feature`이면 자산/구간 범위만 좁히고 위 해당 항목을 모두 확인한다. `audit`이면 파일 생성·편집·설치 없이 기존 자료로 확인한 결과와 공백을 대화로만 보고한다.
