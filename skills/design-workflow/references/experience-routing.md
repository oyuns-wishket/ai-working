# 웹사이트 목적과 도구 선택

검토일: 2026-09-14. 아래는 선택 기준이다. 특정 제품을 항상 설치하거나 새 stack으로 이관하라는 지시가 아니다. 역할 분류는 현재 작업 범위에만 적용한다.

## 주 목적

| 사용자에게 필요한 결과 | 먼저 확정할 것 | 읽을 참조 | 기본 선택 방향 |
|---|---|---|---|
| 업무 UI: 등록·검색·수정·승인 | 핵심 과업, 정보 밀도, 입력/복구 흐름 | [web-quality.md](web-quality.md) | 기존 UI·semantic HTML·CSS; 복잡한 상호작용에만 Motion 등 |
| 데이터 대시보드: 비교·추세·이상 탐지 | 지표 정의, 기간, 비교 기준, 다음 행동 | [data-surfaces.md](data-surfaces.md) + web quality | 기존 표·차트 우선; Bklit UI·Recharts·ECharts는 조건부 후보 |
| 홍보·콘텐츠: 이해·신뢰·신청 | 독자, 핵심 메시지, 증거, CTA, 검색/공유 | web quality; 모션 필요 시 [motion-and-3d.md](motion-and-3d.md) | 읽기 흐름과 HTML 콘텐츠 우선; CSS → 목적에 맞는 모션 |
| 3D 체험: 제품 탐색·구조 설명·공간 경험 | 모델 보유, 정확도, 회전/분해/변형, 모바일 | motion and 3D + web quality | 자산 생성·렌더링·스크롤 제어를 따로 선택 |

마케팅 랜딩과 로그인 후 대시보드는 서로 다른 목적이다. 보조 역할을 추가할 수 있으나 필요 없는 참조까지 전부 읽지 않는다. 단순 KPI 한 개 때문에 차트 엔진을 추가하지 않는다. 지도·편집기 등 표 밖의 요구는 기존 구성과 공식 자료를 조사해 같은 기준으로 선택하고 억지로 위 도구에 맞추지 않는다.

## 선택 순서

1. 기존 의존성·컴포넌트로 충족 가능한지 실제 예제를 확인한다.
2. 사용자의 핵심 과업에 필요한 표현과 상호작용을 정의한다.
3. 추가가 필요하면 주 후보 하나와 의미 있는 대안만 비교한다. CSS/추가 설치 없음도 후보에 포함한다.
4. stack/버전·SSR·접근성·모바일·로드 비용·라이선스·유료 기능·내보내기 제약을 공식 문서에서 확인한다. 저장소 별표 수나 홍보 영상만으로 적합성을 확정하지 않는다.
5. 선택 이유와 제약을 기존 DESIGN 또는 구현노트에 짧게 남긴다. 사용자가 이미 선택한 제품·유료 사용 범위는 재확인하지 않고 유지한다. 새 결제·고객 자산 업로드·외부 배포는 기존 승인을 확대해 수행하지 않는다.

## 필요한 결정 기록

| 항목 | 기록 예 |
|---|---|
| 모드 / 주 목적 | small-feature / 데이터 대시보드 |
| 사용자가 할 일 | 기간을 바꾸고 매출 감소 채널을 찾는다 |
| 재사용 / 추가 도구 | 기존 chart component / 추가 없음 |
| 선택 이유 / 제외 대안 | 기존 토큰·키보드 동작 유지 / 새 차트 엔진 불필요 |
| 확인할 상태 / 제약 | 0과 누락 구분, 느린 조회, 모바일 범례 |
| 증거 | 대상 route·대표 데이터·검증 결과 |

이 표를 또 다른 필수 문서로 만들지 않는다. 기존 정본에 같은 정보가 있으면 링크한다.

## AI 제작 서비스의 위치

[Manus Webapp](https://www.manus.im/features/webapp)은 사이트를 생성하는 서비스이며 앱에 설치하는 UI 라이브러리가 아니다. 사용자가 외부 빌더를 원하거나 초기 시제품에 적합할 때만 선택한다. 기존 고객 앱을 자동 이관하지 않는다. [운영 과금](https://help.manus.im/en/articles/13885710-how-does-webdev-billing-work), 코드/데이터 내보내기와 실제 인증·배포 구조를 확인한다. 생성 결과도 같은 디자인 게이트와 구현 검증을 통과해야 한다.
