# 웹 화면의 완성도와 체감 품질

검토일: 2026-09-15. 웹 화면 전반의 정렬·가독성·조작·반응형·성능 판단 기준을 소유한다. 기존 브랜드·프로젝트 수용 기준이 우선이며 모든 화면을 같은 수치나 패턴으로 만들지 않는다. 관련 항목만 구현·검증에 적용한다. 업무 UI(표·폼·필터바·키보드 입력·밀도·권한별 상태)의 상세 기준은 [work-ui-surfaces.md](work-ui-surfaces.md), 차트·지표·데이터 정확성은 [data-surfaces.md](data-surfaces.md)가 소유하며 이 문서는 그 규칙과 같은 용어·숫자로 요약만 한다.

## 정렬·구조

- 페이지 제목, 설명, toolbar, 본문이 공유할 주요 좌우 축을 정한다. 서로 다른 container 폭과 임의 margin으로 축이 흔들리지 않게 한다.
- 반복 행·카드의 padding, label/value 간격, action 위치를 일관되게 한다. 모든 카드를 같은 높이로 강제해 빈 공간이나 잘림을 만들지 않는다.
- 실제 글자와 아이콘을 보고 baseline·시각적 중앙을 맞춘다. 인접 입력/버튼의 높이와 간격을 확인한다.
- 정보 묶음 사이와 묶음 내부 간격을 구분한다. 모든 내용을 카드로 감싸거나 구분선·그림자를 중복하지 않는다.
- 도구 막대·sticky header가 본문, anchor 대상, 키보드 focus를 가리지 않게 한다.

## 가독성·밀도

- 제목→설명→핵심 값→보조 정보의 읽는 순서를 만든다. 주 행동을 구별하고 동일한 시각적 강조를 남발하지 않는다.
- 기존 type/spacing scale을 재사용한다. 긴 한글·영문·숫자·단위를 실제 내용으로 확인하고 글자를 줄여 overflow를 감추지 않는다.
- 데이터 화면은 비교할 숫자에 자릿수 정렬·일관된 단위/정밀도·필요 시 tabular numerals를 적용한다. ID는 숫자 크기 비교 대상으로 취급하지 않는다. 표 안의 열 정렬(텍스트 좌/숫자 우/상태 통일)·단위 위치·자릿수 고정 규칙은 [work-ui-surfaces.md](work-ui-surfaces.md) §1.1을 따른다.
- 업무 화면은 관련 정보를 함께 볼 수 있는 밀도를, 읽는 페이지는 문장 길이와 호흡을 우선한다. 밀도 조절 기능은 실제 필요할 때만 추가한다. 판정: 결정에 필요한 값을 보려고 스크롤·탭 전환을 반복하면 밀도가 낮은 것이고, 관련 없는 값이 섞여 스캔이 느려지면 위계가 없는 것이다. 밀도 단계·행 높이·기본 밀도 판정은 [work-ui-surfaces.md](work-ui-surfaces.md) §1.2와 §5를 따른다.
- 업무 화면에서 표·목록·폼을 카드로 감싸 여백·테두리·그림자를 중복하지 않는다. 카드 안에 카드가 있거나 같은 위계의 카드가 여섯 개 이상 나열되면 재검토한다([work-ui-surfaces.md](work-ui-surfaces.md) §5).
- 업무 화면의 텍스트 위계는 표 본문·라벨·보조 텍스트 세 단계 이내로 제한하고, 강조는 굵기와 색 하나로 한다. 크기 증가는 제목에만 쓴다.
- 상태는 색 + 텍스트 라벨/아이콘/위치로 표시한다. 행 배경색만으로 상태를 구분하면 결함이다.
- ERP·관리자 화면이라는 이유로 가독성 기준을 낮추지 않는다. "고도화된 가독성"의 판정은 대표 과업의 완료 시간·오류·재입력이며, 표·폼·필터바·키보드 입력·권한별 상태의 상세 기준과 검증 항목은 [work-ui-surfaces.md](work-ui-surfaces.md)가 소유한다. 업무 UI 목적이면 그 문서를 필수로 읽고 `small-feature`도 해당 항목을 전부 확인한다.

## 조작·피드백

- 입력 label은 placeholder로 대체하지 않는다. 오류는 해당 입력에 연결하고 입력값과 복구 경로를 보존한다.
- 클릭·제출 직후 선택/처리 상태를 표시한다. 중복 제출을 막되 성공하기 전에 성공 toast나 상태를 확정하지 않는다.
- 조회 중 안정된 공간을 유지한다. skeleton은 실제 구조에 맞추고, 갱신 중 기존 데이터가 남으면 오래된 상태임을 명료하게 표시한다.
- empty(아직 없음), no results(조건 불일치), error(실패), permission denied를 구분하고 가능한 다음 행동을 안내한다.
- modal dialog/drawer의 focus 이동/복귀, Esc, 배경 조작 차단은 기존 accessible primitive와 WAI-ARIA 패턴을 따른다. 비모달 패널에 focus trap을 강제하지 않는다. hover-only 정보는 키보드·터치에서도 접근 가능해야 한다.
- URL·뒤로가기·선택 상태·검색어 유지 등 기존 동작을 보존한다. 새 기능으로 확장할 필요가 있으면 범위를 먼저 대조한다.
- 폼의 라벨 위치·그룹·필수 표시·오류 위치·저장/제출 상태·자동 저장·이탈 경고·Enter/Tab 동작, 필터바의 기본값·적용 상태·URL 동기화, 인라인 편집 상태, 권한별 읽기 전용 표시의 판정 기준은 [work-ui-surfaces.md](work-ui-surfaces.md) §1.5, §2, §3을 따른다.

## 반응형·접근성

- 작은 화면은 desktop을 축소한 형태로 처리하지 않는다. 주요 행동과 정보 순서를 유지하면서 열·메뉴·보조 정보를 재배치한다.
- 내용이 깨지는 폭, 긴 텍스트, 200% 확대([WCAG resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)), 키보드와 실제 touch를 확인한다. 필수 정보가 넓이 부족 때문에 사라지지 않아야 한다.
- 320 CSS px 폭에서 일반 콘텐츠가 양방향 스크롤을 요구하지 않게 한다. 데이터 표·지도처럼 2차원 배치가 필요한 영역은 별도 스크롤과 접근 경로를 제공한다. [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). 표의 모바일 대안(카드 변환 또는 별도 스크롤 + 식별 열 고정) 판정은 [work-ui-surfaces.md](work-ui-surfaces.md) §1.8을 따른다.
- 본문 대비 4.5:1, 큰 글자와 관련 UI 경계 3:1을 기준으로 확인하고 색만으로 상태를 구분하지 않는다.
- 모바일 주요 조작은 44×44 CSS px 이상을 사용성 목표로 둔다. 이는 WCAG 2.2 AA의 일률적 최소치가 아니다. AA target size는 24×24 CSS px 또는 명시된 간격/예외 조건을 따로 평가한다. [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- 콘텐츠·상태·차트 요약은 읽을 수 있는 HTML로 제공한다. canvas나 이미지 안의 글자만으로 핵심 정보를 전달하지 않는다.

## 성능·웹 전달

- 핵심 콘텐츠와 주요 행동을 첫 로드에서 사용할 수 있게 한다. 이미지·폰트·차트·3D 자산이 레이아웃을 밀지 않도록 공간을 예약한다.
- SSR/SSG/CSR은 프로젝트 방식을 따른다. 공개 페이지의 주요 설명을 client-only canvas에 가두거나 3D 때문에 페이지 전체를 불필요하게 client component로 바꾸지 않는다.
- 역할에 필요한 무거운 코드는 해당 route/구간에서만 로드한다. 중요한 첫 화면 이미지까지 무조건 lazy-load하지 않는다. 폰트 fallback·이미지 크기·한국어 글리프를 확인한다.
- 성능 영향이 있는 변경은 대표 기기·network·cache 조건을 기록해 전후 측정한다. 성능 영향의 판정 기준(차트/모션/3D 엔진 추가·교체, canvas/WebGL/영상 자산 도입, 가상화·대량 데이터, 번들에 새 runtime 추가 중 하나면 영향 있음)은 [verification.md](verification.md)가 소유한다. [Core Web Vitals](https://web.dev/articles/vitals)의 좋은 기준은 LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1이며 실제 사용자 방문의 75th percentile 기준이다. 로컬 Lighthouse 점수는 운영 field 통과 증거가 아니고 TBT를 INP로 보고하지 않는다.
- 서비스에 field 데이터가 없으면 그 부재를 명시하고 lab 측정·직접 조작 근거만 보고한다. 통계가 없다는 이유로 제품을 임의 배포하거나 추적 서비스를 추가하지 않는다.

## 마감 검토

대표 과업 하나를 직접 수행하고 아래 네 질문으로 판단한다.

1. 처음 보는 사람이 목적과 다음 행동을 알아볼 수 있는가?
2. 정보의 축·단위·위계가 일관되고 읽기 쉬운가?
3. 입력부터 완료까지 상태가 명확하며 실패해도 복구 가능한가?
4. 모바일·키보드·느린 로드에서도 중요한 과업을 완료하는가?

새로 발견한 범위 내 결함을 고친 뒤 관련 검증을 반복한다. 임의 만족도 점수·과장된 완료 문구 대신 관찰과 사용자 피드백을 구분한다.
