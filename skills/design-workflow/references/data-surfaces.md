# 데이터 대시보드와 차트

검토일: 2026-09-15. 수치를 통해 어떤 결정을 하는지 먼저 확인한다. 기존 데이터 계약을 새 디자인에 맞춰 바꾸지 않는다. 이 문서는 **차트·지표 정의·데이터 정확성·차트 엔진 정책**을 소유한다. 표(데이터 그리드)·폼·필터바·키보드 입력·밀도·권한별 상태는 [work-ui-surfaces.md](work-ui-surfaces.md)가 소유하며, 대시보드의 상세 표도 그 문서의 §1을 따른다. 모드·게이트·도구 기본값은 SKILL.md를 따른다.

## 지표와 시각 표현

- 지표 이름·정의·단위·시간대·기간·비교 기간·집계 범위·갱신 시점을 확인한다. API/쿼리로 확인 가능한 것은 사용자에게 되묻지 않는다.
- 0, null/누락, 조회 중, 조회 실패를 구분한다. 분모 0의 증감률이나 미수집 데이터를 임의 0%로 표시하지 않는다.
- 카드·차트·상세 표가 같은 필터와 집계를 사용해야 한다. 샘플 데이터는 샘플로 표시한다. 필터바 계약은 [work-ui-surfaces.md](work-ui-surfaces.md) §3과 같다.
- 추세는 선, 항목 비교는 막대, 정확한 값·검색·업무 처리는 표가 출발점이다. 목표/분모가 없는데 장식용 gauge를 넣지 않는다. 복잡한 차트는 사용자의 판단을 더 쉽게 할 때만 선택한다.
- 단위·축·범례·tooltip·색의 의미를 일관되게 한다. 축 절단과 집계/샘플링으로 의미가 달라지면 명시한다. 색 외에 label/pattern을 제공한다.
- 지표 정의는 화면에서 접근 가능해야 한다(제목 tooltip·설명·정의 링크 중 하나). 같은 이름의 지표가 화면마다 다른 정의를 가지면 결함이다.

## 차트 작업의 기본 경로

차트 작성·디자인 변경에는 **Bklit UI를 기본 도구로 적용**한다. 기존 Bklit source가 있으면 재사용하고 없으면 [tooling.md](tooling.md)에 따라 필요한 chart component를 로컬에 추가한다. package.json만 보지 말고 shadcn registry·생성된 소스도 확인한다. 같은 저장소에 ECharts·Chart.js·ApexCharts·Highcharts·구 Recharts wrapper 등 **레거시 엔진이 있으면(대상 화면이 아닌 다른 화면에만 있어도) 아래 [레거시 차트 엔진 교체](#레거시-차트-엔진-교체) 절을 같은 작업 안에서 따른다**. 기존 다른 엔진이 있다는 사실만으로 Bklit 검토를 생략하지 않는다.

새 차트 방향을 만들기 전에 채택 후보의 공식 실행 예제를 브라우저에서 직접 조작한다. 예제 URL·확인한 행동·보이는 결과와 이번 시안에 가져올 표현을 짧게 기록한다. 선과 영역의 질감, 축·숫자의 위계, tooltip·crosshair, 범례 선택과 데이터 전환 중 실제 과업에 필요한 것을 지정한다. 문서·소스 읽기나 설치 성공을 동작 관찰로 기록하지 않는다. 직접 관찰이 미완료이면 새 방향의 최종 채택과 application source 구현을 보류한다. 접근 가능한 실행본이 있으면 결정을 묻지 않고 직접 조작한다. 접근 불가(URL 응답 실패·로컬 실행 실패의 실제 근거)가 확인된 경우에만 사용자에게 접근 가능한 공식 실행본 확보·공식 소스의 로컬 실행·해당 방향 보류 중 하나를 결정받는다. 대체 자료와 진행 요청은 직접 관찰 완료를 대신하지 않는다. 관찰 없이 채택하는 선택지는 없다. 접근 불가 시 실제 확인한 공식 영상·문서·소스는 "대체 근거(관찰 아님)"로 구분해 기록하고 브라우저에서 확인했다고 주장하지 않는다. 기록 위치와 write 권한은 현재 모드를 따른다(`audit`는 대화로 보고).

새 차트 표현은 같은 대표 데이터와 지표로 **동작 시안 세 개**를 함께 보여주고 AI 추천·사용자 선택을 기록한다. 축·범례·tooltip·필터·업데이트 동작과 모바일을 직접 비교한다. 의미에 맞는 chart type은 먼저 결정하고 세 안을 채우려고 부적절한 원형·선·막대를 섞지 않는다. 세 안의 차이는 같은 차트 영역을 비교해도 **표현·정보 위계·탐색 동작** 세 축 중 **최소 두 축**에서 드러나야 한다(판정 기준은 아래 [동작 시안 세 개의 판정 기준과 예시](#동작-시안-세-개의-판정-기준과-예시)). 배치·색상·설명 이름만 바꾼 안으로 채우지 않는다. 필요한 표현을 선택하며, 예제의 모든 효과를 복제하거나 차트 의미를 바꾸지 않는다. 정지 이미지·외부 예제 링크만으로 시안을 대체하지 않는다.

### 동작 시안 세 개의 판정 기준과 예시

세 안은 아래 세 축 중 **최소 두 축**에서 서로 달라야 하고, 각 안을 같은 대표 데이터·같은 필터·같은 대표 행동(예: 기간 변경 → hover → 항목 선택)으로 직접 조작할 수 있어야 한다.

| 축 | 달라야 하는 것 | 같은 것으로 취급하는 것(부적합) |
|---|---|---|
| 표현 | 선/영역 질감, marker·cap, 채움·pattern, 축·그리드 밀도, 숫자 위계 | 색상만 교체, 제목 문구만 변경 |
| 정보 위계 | 무엇이 먼저 읽히는가: 합계/KPI 우선, 추세 우선, 비교 대상 우선 | 카드 배치 순서만 변경 |
| 탐색 동작 | hover/pin/crosshair, 범례 토글, 기간 brush/zoom, 선택 → 표 연동 | duration/easing 수치만 변경 |

예시 세트(각 프로젝트의 대표 데이터로 치환한다):

| 대표 데이터 | 안 A: 간결한 업무형 | 안 B: KPI와 추세 중심 | 안 C: 비교·탐색 중심 |
|---|---|---|---|
| 월별 매출 추세(12개월, 목표 포함) | 얇은 선 + 마지막 점 marker, 축 숫자 절제, hover 시 단일 tooltip. 표와 같은 정밀도 | 상단 KPI(당월·증감률) + 영역 채움 추세, 목표선 표시, hover 시 KPI가 선택 지점 값으로 갱신 | 당해·전년 두 선 비교, 범례 토글, 기간 brush로 확대, 선택 지점이 아래 표 행을 하이라이트 |
| 채널별 매출 비교(채널 6개, 기간 필터) | 수평 막대 정렬(값 내림차순), 값 라벨, hover 최소 | 채널별 합계 KPI 행 + 막대, 상위 채널 강조, 기간 변경 시 막대 길이 전환 | 기간 A/B 그룹 막대 또는 stacked bar 전환, 채널 클릭 → 해당 채널 추세 drill-down, 범례로 채널 제외 |
| 창고별 재고 분포(창고 4개 × 품목군 5개) | 단순 stacked bar, 품목군 pattern 구분, tooltip에 수량·비율 | 총 재고 KPI + 안전 재고 미달 품목군 강조, 미달 항목만 색 경고 + 라벨 | 창고 선택 → 품목군 분포로 전환, 품목군 hover 시 모든 창고에서 같은 항목 강조, 표와 동기 |

판정:

- 세 안 모두 같은 chart type 결정을 공유해야 한다(추세=선, 비교=막대). 안을 채우려고 원형을 섞으면 부적합이다.
- 한 안이라도 정지 이미지이거나 대표 행동을 실제로 조작할 수 없으면 시안 세 개로 인정하지 않는다.
- AI 추천 하나와 이유를 붙인다. 사용자가 시안을 본 뒤 위임하면 그 범위에서 결정하고 기록한다. `ㄱㄱ`·`알아서`는 아직 보여주지 않은 시안의 승인이 아니다(SKILL.md).

신규 화면에서는 메인 skill의 세 composition 안에 이 비교를 통합한다. 기존 화면에서 새로운 차트 방향만 추가하면 해당 영역만 비교한다. 이미 승인된 chart 패턴의 작은 수정은 선택을 재요청하지 않고 재사용 근거와 변경 상태를 확인한다.

Bklit은 React/shadcn 기반이다. 비React, 프로젝트의 명시적 다른 엔진 계약, 필수 기능 부재 또는 대표 데이터 실측 성능 문제가 있으면 근거와 대안을 보여주고 필요한 결정만 받는다([호환성과 대안](#호환성과-대안)). 여기서 **계약**은 `AGENTS.md`/`CLAUDE.md`/`DESIGN.md` 또는 사용자 발화에 기록된 명시 결정만 뜻한다. 기존 import·wrapper의 존재는 계약이 아니라 인벤토리 대상이다. 기존 다른 엔진이 있다는 사실만으로 Bklit 검토를 생략하지 않는다. 승인 없이 이번 범위 밖 화면을 교체하지 않는다. 전체 이관은 아래 절의 **전체 이관 제안 → 승인** 순서를 따른다. 차트 추가가 필요 없는 단순 숫자 표시에는 이 경로를 강제하지 않는다.

## 승인된 차트 체계의 재사용과 확장

- 공식 예제의 완성도는 chart import가 아니라 선·채움·패턴·축·tooltip·선택 상태의 조합에서 나온다. 채택한 조합을 프로젝트 톤으로 옮기고, 차트마다 공식 예제의 배경·색상을 그대로 가져와 서로 다른 테마를 만들지 않는다. 차트 자체의 비교가 목적이면 큰 제목·합계·주변 패널이 실제 plot을 밀어내지 않는지 확인한다.
- 승인된 시안의 surface·palette·typography·단위·정보 위계와 상태별 표현을 기존 DESIGN/공통 컴포넌트 계약에 기록한다. 사용자 선택이 작은 cap·절제된 marker라면 재사용 시 ring·glow를 임의 복원하지 않는다. 반대로 승인된 질감·모션을 업무 UI라는 이유로 제거하지 않는다. 특정 색·서체·marker 형태는 해당 프로젝트의 선택이며 전역 기본값이 아니다.
- 다른 차트 종류는 사용자의 판단 과업과 데이터 의미로 고른다. 예: 구성 비교는 stacked bar, 분포는 histogram, 상관은 scatter. 승인된 시각 체계를 공유하되 각 종류의 축·분모·범례·상호작용은 대표 데이터로 확인한다. 새 종류라는 이유만으로 디자인 인터뷰·세 시안을 다시 시작하지 않고, 새로운 시각 방향이나 미승인 핵심 동작이 필요한 부분만 기존 선택 과정으로 다룬다.
- 기간 변경·hover·pin·keyboard 선택에서 같은 항목이 marker·tooltip·요약·표에 일관되게 연결되어야 한다. 선택일 수치 옆에 기간 전체 증감률이 남으면 집계 범위를 명시한다. 의미 있는 데이터 갱신은 기존 geometry를 이어서 전환하고, 값이 바뀔 때마다 전체 chart를 remount해 탐색 상태를 잃지 않게 한다. 의도적인 재생·초기화는 별도 동작으로 둔다.
- 프로젝트 전체 적용을 요청받으면 실제 차트 사용처를 조사해 공통 토큰·wrapper와 종류별 예외를 구분하고 승인 범위에서 이관한다. 레거시 엔진이 있으면 아래 절의 인벤토리·순서·완료 증거를 그대로 사용한다. 샘플 시안의 승인을 실제 데이터·권한·loading/empty/error 계약 검증으로 간주하지 않는다. 설치나 공통 wrapper 수정만으로 모든 화면 적용이 끝났다고 보고하지 않는다.

## 레거시 차트 엔진 교체

레거시 엔진(ECharts, Chart.js, ApexCharts, Highcharts, nivo, Victory, Plotly, 구 Recharts wrapper 등)은 **교체 대상**이다. 공존은 과도기와 기록된 예외에만 허용하고 장기 상태로 두지 않는다. 이 절은 차트 작업 중 같은 저장소에서 레거시 엔진을 발견한 **모든 모드**에 적용한다(`new`는 기준선 화면이 없으므로 대상 화면 이관·parity는 N/A이지만, 같은 저장소에 레거시 엔진이 있으면 인벤토리·판정·전체 이관 제안·공존 기록은 그대로 적용한다; `audit`는 인벤토리·판정·전체 이관 **제안**까지만 대화로 보고하고 이관·설치·제거·기록 파일 생성은 하지 않는다). `new`에서 새로 만드는 화면은 레거시가 없으므로 인벤토리 행이 아니며 N·M에 넣지 않는다. 레거시 화면이 남아 있으면 `new`의 완료 보고에도 아래 4. 공존 규칙의 "부분 적용: N/M 화면 이관, 나머지 제안 중" 형식과 잔여의 3구분·전체 이관 제안을 포함한다. 이 문장은 SKILL.md `### 레거시 차트 엔진 교체 정책(요지)`·[project-audit.md](project-audit.md)·[tooling.md](tooling.md)가 같은 뜻으로 반복한다.

### 1. 인벤토리

조사 단계([project-audit.md](project-audit.md)의 차트 엔진 인벤토리)에서 프로젝트 전체의 엔진 사용처를 수집한다. 인벤토리 없이 차트를 수정하지 않는다. 예:

```bash
rg -n "echarts|chart\.js|chartjs|apexcharts|highcharts|recharts|nivo|victory|plotly" src --glob '!**/*.test.*'
rg -n "\"(echarts|chart\.js|apexcharts|highcharts|recharts|@nivo|victory|plotly\.js)" package.json
```

[project-audit.md](project-audit.md) 차트 엔진 인벤토리의 두 번째 검색(Bklit/shadcn chart source 검색, 예: `bklit`·`components/ui/chart`·`ChartContainer`) 결과는 생성 소스와 호출부를 포함하는 후보 목록이다. registry 원본·설치 증거로 생성 출처를 확인한 파일의 실제 하위 의존성 import(예: 생성된 `components/ui/chart*`가 import하는 `recharts`)만 제외하고 `Retained dependencies` 후보로 분류한다(계수 단위는 아래 3. 순서 1). 호출 화면·프로젝트 wrapper의 레거시 import는 검색 결과가 겹쳐도 제외하지 않는다. 예: `echarts`와 `ChartContainer`를 함께 import하는 page 파일은 두 검색에 모두 잡히지만 레거시 사용처다. 프로젝트가 직접 작성한 recharts 기반 wrapper는 **구 Recharts wrapper**로 레거시다. 결과를 표로 기록한다(DESIGN.md `Legacy chart engine migration`의 Legacy inventory, 또는 gate template `Legacy chart engine migration` 항목에 링크한 구현노트). 한 route에 차트가 여러 개이면 route는 1행이고 사용처(파일) 열에 파일을 모두 적는다. 공통 wrapper 하나가 여러 route에서 쓰이면 route마다 행을 만든다:

| 화면/route | 엔진 | 사용처(파일) | 공통 wrapper | 테마/토큰 파일 | 차트 종류 | 비고(export·zoom 등 사용 기능) |
|---|---|---|---|---|---|---|

### 2. 판정

- React/shadcn 호환 프로젝트이면 **Bklit로 이관이 기본**이다.
- **호환의 정의**: React이고, shadcn `components.json`과 Tailwind 기반 chart source를 기존 CSS 체계와 충돌 없이 추가할 수 있는 경우다. 이미 shadcn/Tailwind가 있으면 호환이며 결정을 묻지 않는다. React이지만 기존 CSS 체계(MUI·CSS Modules·styled-components·Emotion 등)에 Tailwind/shadcn **도입**이 필요하면 아래 네 예외에 해당하지 않으므로 예외로 기록하지 않고, 도입 diff(`components.json`·Tailwind 설정·전역 CSS 변경)·영향 범위(기존 스타일 충돌·번들·빌드 설정)·토큰 매핑(기존 색·서체·spacing → CSS variables)을 제시한 뒤 **그 도입 결정 하나만** 받는다. 도입 승인이면 Bklit 기본 경로를 그대로 따른다. 거부이면 "프로젝트의 명시적 다른 CSS 체계 결정"을 사용자 메시지 원문과 함께 예외 2(명시적 계약)로 기록하고 [예외 판정을 통과한 뒤의 대안 순서](#예외-판정을-통과한-뒤의-대안-순서)를 따른다. 이 결정 없이 전역 CSS 체계를 추가하지 않는다. 설치 절차는 [tooling.md](tooling.md) `## 앱 라이브러리 설치·재사용`을 따른다.
- 비호환 예외는 SKILL.md의 기본 도구 선언과 같은 네 가지뿐이며, 예외는 근거와 함께 gate template의 `Legacy chart engine migration` 항목과 DESIGN.md의 `Legacy chart engine migration` 절에 기록한다([gate template](../assets/design-gates.template.md), [DESIGN template](../assets/DESIGN.template.md)).
  1. **비React**(Vue·Svelte·Angular·서버 템플릿 등) → Bklit 비호환. 프레임워크를 이관하지 않는다.
  2. **프로젝트의 명시적 다른 엔진 계약** → `AGENTS.md`/`CLAUDE.md`/`DESIGN.md` 또는 사용자 발화에 기록된 **명시 결정**만 뜻한다. 기존 import·wrapper의 존재는 계약이 아니라 인벤토리 대상이다. 계약이 있으면 파일·문장(또는 사용자 메시지 원문)을 인용해 기록하고, 사용자에게 계약 유지 여부를 결정 하나로 확인한다.
  3. **필수 기능 부재** → 사용자 과업에 필요한 기능(예: 대규모 시계열 zoom·특정 차트 종류)을 Bklit 공식 component·source에서 확인했는데 없고, 우회가 불가능함을 **구체 기능명과 확인한 문서/소스**로 남긴다. "다양한 기능"처럼 일반적인 이유는 근거가 아니다.
  4. **대표 데이터 실측 성능 문제** → 실제 데이터 규모·기기·측정값을 기록한 뒤에만 인정한다. 추정은 근거가 아니다.
- 예외에 해당하지 않으면 "기존에 ECharts를 쓰고 있다", "다른 화면이 아직 ECharts다", "일정이 촉박하다"는 유지 사유가 아니다. 레거시 차트를 **"스타일만 손보는" 선택지는 만들지 않는다**.
- 예외의 단위: 예외 1(비React)·2(명시적 계약)는 그 계약이 적용되는 범위(보통 프로젝트 전체)의 모든 차트에 적용되며 [예외 판정을 통과한 뒤의 대안 순서](#예외-판정을-통과한-뒤의-대안-순서)를 따른다. 예외 3(필수 기능 부재)·4(실측 성능)는 **개별 차트 단위**로 근거를 기록한다. 예외에 해당하는 차트는 그 엔진을 유지하되 공통 토큰·상태 계약을 승인된 차트 체계에 맞추고, 예외 범위 밖의 차트는 계속 교체 대상이다.
- 같은 화면 안 개별 차트 예외의 처리(모든 파일 동일 문장): 확인된 개별 차트 예외가 없는 화면은 모든 레거시 차트를 함께 이관한다. 개별 차트의 비호환 예외(필수 기능 부재·실측 성능)가 기록된 화면은 해당 차트에 한해 공존을 허용하고, 예외 범위·의존 비용·재검토 조건을 기록한다. 해당 route는 `기록된 예외`로 집계하며 `이관 완료`나 레거시 import 0건으로 표시하지 않는다. 그 화면의 예외가 아닌 차트는 여전히 이번 범위이며 Bklit로 이관한다.

### 3. 순서

1. **이번 작업의 대상 화면 이관**: 대상 차트를 Bklit로 구현한다. 새 표현이면 위의 동작 시안 세 개를 거친다. 승인된 표현이면 재사용한다. 대상 화면에 레거시 차트가 여러 개이면 **그 화면의 레거시 차트 전부**가 이번 범위이며, 각 차트는 승인 표현 재사용 또는(새 표현이면) 동작 시안 세 개로 처리한다. 확인된 개별 차트 예외가 없는 화면은 모든 레거시 차트를 함께 이관한다(대상 화면의 레거시 import는 0건이어야 한다). 개별 차트의 비호환 예외(필수 기능 부재·실측 성능)가 기록된 화면은 해당 차트에 한해 공존을 허용하고, 예외 범위·의존 비용·재검토 조건을 기록한다. 해당 route는 `기록된 예외`로 집계하며 `이관 완료`나 레거시 import 0건으로 표시하지 않는다. 기록된 예외 없이 화면의 일부 차트만 이관하고 나머지를 남기는 선택지는 없다.
   - **레거시 import 계수 단위**: "레거시 import 0건"은 **앱 코드(page·route 컴포넌트·component·프로젝트 wrapper·테마 파일)** 에서 레거시 엔진 패키지 또는 그 wrapper를 import/require/dynamic import하는 **파일이 0개**라는 뜻이다. 건수는 파일 단위로 세고 검색 명령·범위·결과를 남긴다([tooling.md](tooling.md) `## 레거시 차트 엔진 제거 절차` 6). shadcn/Bklit registry가 생성한 chart source가 내부적으로 사용하는 하위 의존성(예: `recharts`)은 레거시가 아니며 계수에서 제외하고, 그 경로를 DESIGN.md `Retained dependencies`에 적는다. 제외 대상은 registry 원본·설치 증거로 생성 출처를 확인한 파일의 실제 하위 의존성 import뿐이며, 호출 화면·프로젝트 wrapper의 레거시 import는 검색 결과가 겹쳐도 제외하지 않는다(위 1. 인벤토리). **구 Recharts wrapper**는 registry 생성 소스가 아닌, Bklit 도입 이전에 프로젝트가 직접 작성한 recharts 기반 chart 컴포넌트/wrapper를 뜻하며 교체 대상이다. 하위 의존성 보존은 구 wrapper를 유지할 근거가 아니다.
2. **동일 데이터 parity 검증**: 같은 route·필터·기간·데이터·theme·viewport·auth로 이전 엔진과 대조한다. 항목: 수치(합계·각 점·증감률), 필터/기간 반영, tooltip 내용·정밀도, 범례 항목·토글, export(있으면 형식·내용), loading/empty/error/권한 상태, 키보드/터치 접근, 모바일. 실행 절차와 parity 표 형식은 [verification.md](verification.md) `## 레거시 차트 엔진 교체 parity 검증`을 따른다. 차이는 표로 남기고 승인된 시각 변경과 기능/데이터 손실을 구분한다.
3. **전체 이관 제안**: 인벤토리에 근거해 남은 화면의 범위·순서(사용 빈도·의존 wrapper 순)·예상 회귀(공유 wrapper, 테마, export 계약, 테스트)·필요한 결정을 사용자에게 제시한다. 이 제안은 이번 작업의 완료 보고에 포함한다.
4. **승인 시 이관**: 승인된 범위·순서대로 화면별로 1–2를 반복한다. 승인 전에는 대상 화면 밖의 차트를 바꾸지 않는다.
5. **레거시 의존성·wrapper·테마 제거**: 마지막 사용처가 사라진 뒤 패키지·wrapper·테마 파일·타입·테스트 fixture를 제거하고 build/lint/test를 실행한다. 사용처가 남았는데 패키지를 제거하지 않는다. Bklit 생성 소스가 실제 사용하는 하위 의존성은 구 wrapper와 구분해 보존한다. 제거 절차는 [tooling.md](tooling.md) `## 레거시 차트 엔진 제거 절차`를 따른다.
6. **완료 증거**: 아래 표를 채운다. 인벤토리의 모든 행이 `이관 완료` 또는 `기록된 예외`가 되기 전에는 완료가 아니다.

### 4. 공존 규칙(과도기)

- 과도기 동안 **이관 완료 화면과 미이관 화면 사이**의 색·서체·숫자 형식·tooltip 정밀도·상태 표현을 공통 토큰에 맞춘다. 같은 화면 안의 공존은 위 순서 1의 **기록된 개별 차트 예외**(필수 기능 부재·실측 성능)에만 허용하며 그 route는 `기록된 예외`로 집계한다. 기록된 개별 차트 예외가 없는데 두 엔진이 섞여 있던 화면은 그 화면 전체를 한 번에 이관한다. 화면 간 테마 차이가 남으면 그 사실을 완료 증거 표의 비고에 적고 다음 이관 범위에 포함한다.
- 같은 데이터에 두 엔진을 동시에 그리지 않는다. 같은 차트 종류를 화면마다 다른 엔진으로 새로 만들지 않는다.
- 과도기 상태의 보고는 반드시 **"부분 적용: N/M 화면 이관, 나머지 제안 중"** 형식이다. "적용 완료"로 쓰지 않는다.
- **N·M의 단위**: N·M은 위 1. 인벤토리 표의 **화면/route 행 수**(고유 route 기준)다. 공통 wrapper·테마·타입 파일은 행이 아니며 N·M에 넣지 않는다. 한 route에 차트가 여러 개여도 route는 1행이고, 그 route의 레거시 차트 전부가 이관돼야 N에 더한다. 공통 wrapper 하나가 여러 route에서 쓰이면 route마다 행을 만든다. 파일·import 수(사용처 파일 수, 공통 wrapper 수)는 별도 값으로 함께 기록하고 화면 수로 바꿔 쓰지 않는다. 예: "사용처 파일 7(공통 wrapper 1) / 화면 5 → 부분 적용: 1/5 화면 이관, 나머지 제안 중".
- **잔여의 3구분**: 보고와 완료 증거 표에서 다음 세 값을 분리한다. (a) **실제 레거시 잔존 사용처** = 레거시 import가 남은 행 수(= `기록된 예외` + `제안 중`; 두 값이 다르면 인벤토리 상태가 틀린 것이므로 상태를 먼저 고친다), (b) **기록된 예외** = 근거와 함께 예외로 기록된 행, (c) **미처리 이관 대상** = 인벤토리 총 행 수 − `이관 완료` − `기록된 예외`. 상태가 `이관(parity 미실행)` 또는 `이관(parity 실패)`인 행은 레거시 import가 0이므로 (a)에 넣지 않지만 `이관 완료`가 아니므로 N에 더하지 않고 (c)에는 포함되며, `이관(parity 실패)` 행은 실패 항목과 수정·재검증 계획을 함께 기록하고, 그 행 수와 해소 계획(fixture 기반 재대조)을 보고 문장 뒤에 한 줄로 덧붙인다(예: "부분 적용: 1/5 화면 이관, 나머지 제안 중. 이관(parity 미실행) 1 화면: fixture 재대조 예정"). 미처리 이관 대상이 0이어도 기록된 예외가 있으면 실제 잔존 사용처는 0이 아니며 "레거시 없음"으로 보고하지 않는다.
- 기록된 예외 외의 공존이 다음 작업에서도 남아 있으면 그 작업의 완료 보고에 다시 전체 이관 제안을 포함한다.

### 5. 완료 증거 표

| 화면/route | 이전 엔진 | 이후 | 대상 화면 레거시 import 건수(파일 수) | parity 결과(수치 대조·필터/기간·tooltip·범례·export·empty/error 상태·키보드/터치·모바일) | 제거된 패키지/파일 | 상태(`이관 완료` / `이관(parity 미실행)` / `이관(parity 실패)` / `기록된 예외: 사유` / `제안 중`) |
|---|---|---|---|---|---|---|

|---|---|---|

| 실제 레거시 잔존 사용처 | 레거시 import가 남은 행 수(= `기록된 예외` + `제안 중`; 두 값이 다르면 인벤토리 상태가 틀린 것이므로 상태를 먼저 고친다) | 고유 route |
| 기록된 예외 | 예외 행 수 + 각 사유 링크 | 고유 route |
| 미처리 이관 대상 | 총 행 수 − `이관 완료` − `기록된 예외` | 고유 route |
| 다음 이관 범위 | 전체 이관 제안의 다음 범위·순서 | route 목록 |

화면 이관률·파일 수와 잔여의 3구분(실제 레거시 잔존 사용처·기록된 예외·미처리 이관 대상) 중 하나라도 비우거나 합쳐 쓰면 완료 증거로 인정하지 않는다. parity 결과는 "동일" 한 단어가 아니라 대조한 항목과 값 차이(있으면 이유)를 적는다. 수치·필터/기간·tooltip·범례·export·상태·키보드/터치·모바일 중 해당 검사가 실패하거나 **미실행**이거나 대상 화면에 레거시 import가 0건이 아니면 대상 화면 이관 완료로 표시하지 않는다. 기준선 실행 불가로 parity가 미실행이면 상태를 `이관(parity 미실행)`으로 두고 N에 더하지 않으며, fixture 기반 재대조로 미실행을 해소한 뒤에만 `이관 완료`로 바꾼다([verification.md](verification.md) `## 레거시 차트 엔진 교체 parity 검증` 3과 같은 문장). 개별 차트 예외가 기록된 route는 `기록된 예외`이며 `이관 완료`나 레거시 import 0건으로 표시하지 않는다. 시각 스냅샷만으로 parity를 통과시키지 않는다.

### 예외 판정을 통과한 뒤의 대안 순서

아래 표는 [레거시 차트 엔진 교체](#레거시-차트-엔진-교체)의 판정에서 네 가지 예외(비React / 명시적 다른 엔진 계약 / 필수 기능 부재 / 실측 성능 문제) 중 하나가 근거와 함께 기록된 **뒤에만** 읽는다. Bklit과 동급의 선택지가 아니며, 예외 근거 없이 이 표의 도구를 고르면 결함이다.

| 순서 | 대안 | 해당 예외 | 범위·제약 | 공식 근거 |
|---|---|---|---|---|
| 1 | 기존 엔진 유지 + 승인된 시각 체계(토큰·숫자 형식·상태) 적용 | 비React; 명시적 계약(기존 엔진이 있는 경우: 엔진 계약 또는 CSS 체계 계약); 개별 차트의 필수 기능 부재·실측 성능 예외(기존 엔진이 그 기능·성능을 실제 충족하는 경우, 위 2. 판정의 예외 3·4) | 예외 범위 안에서만. 범위 밖 차트는 계속 교체 대상 | 프로젝트 소스 |
| 2 | Recharts | 필수 기능 부재(React; 기존 엔진이 없거나 기존 엔진도 해당 기능을 충족하지 못하는 경우), 명시적 CSS 체계 계약(React, 기존 엔진 없음) | 부재 기능을 Recharts가 실제 제공하는지 설치 버전 API·키보드 지원·데이터량으로 확인. 구 Recharts wrapper 자체는 교체 대상 | [API](https://recharts.github.io/en-US/api/), [accessibility](https://github.com/recharts/recharts/blob/main/storybook/stories/API/Accessibility.mdx) |
| 3 | Apache ECharts | 비React, 실측 성능 문제(기존 엔진이 없거나 기존 엔진도 해당 성능을 충족하지 못하는 경우) | 대표 데이터로 성능 측정 기록; ARIA·텍스트 요약·패턴을 명시 설정/확인. React 프로젝트의 기존 ECharts는 예외 근거 없이는 교체 대상 | [Examples](https://echarts.apache.org/examples/en/index.html), [accessibility](https://echarts.apache.org/handbook/en/best-practices/aria/) |

예외 2인데 기존 엔진이 없는 React 프로젝트(예: React + MUI/CSS Modules, Tailwind/shadcn 도입 거부, 차트 엔진 없음): Tailwind 없이 동작하는 React 차트 라이브러리(예: Recharts) 중 필요한 종류·키보드 지원·데이터량을 설치 버전 API로 확인한 후보 하나와 근거를 제시하고 결정 하나를 받는다. 이 경우는 순서 2 행의 해당 예외 '명시적 CSS 체계 계약(React, 기존 엔진 없음)'에 해당한다. 순서 1(기존 엔진 유지)은 유지할 엔진이 없으므로 이 경우에 쓰지 않는다. 새 표현이면 동작 시안 세 개 규칙은 엔진과 무관하게 그대로 적용한다.

비React 판정 순서(예: Vue):

1. 실제 stack(framework·버전·기존 차트 소스)을 확인하고 "Bklit은 React/shadcn 기반이므로 비호환"을 근거와 함께 기록한다.
2. 기존 엔진이 있으면 유지 여부를 판정한다: 기존 엔진이 필요한 표현·접근성·성능을 충족하면 유지하고 승인된 시각 체계(토큰·숫자 형식·상태)를 그 엔진에 적용한다. 충족하지 못하면 해당 framework에서 공식 지원되는 대안을 조사해 후보를 제시한다.
3. 필요한 결정 하나만 받는다(예: "기존 ECharts 유지 + 토큰 정렬" vs "대안 X 도입"). 프레임워크 이관을 제안하지 않는다.
4. 새 표현이면 동작 시안 세 개 규칙은 그대로 적용한다(엔진이 달라도 시안 기준은 같다).

표의 도구를 한꺼번에 넣지 않는다. Bklit 기본 경로 또는 확인한 예외에 맞는 도구 하나를 선택한다. 두 engine의 공존은 **과도기(이관 진행 중이며 실제 레거시 잔존 사용처·기록된 예외·미처리 이관 대상·다음 이관 범위가 기록됨) 또는 기록된 비호환 예외**에만 허용하고, 그때도 범위·중복 비용·과도기 종료 조건(예외는 재검토 조건)을 기록한다. 같은 화면 안의 공존은 기록된 개별 차트 예외에만 허용한다(위 [레거시 차트 엔진 교체](#레거시-차트-엔진-교체) 3. 순서 1). headless 표 로직·차트 컴포넌트·데이터 수집 시스템을 혼동하지 않는다. [tool-capabilities.md](tool-capabilities.md)에 따라 유료 Studio 이용 여부와 chart 코드의 라이선스를 각각 확인한다.

## 직접 검증

1. 대표 데이터에서 카드 합계·차트·표의 값을 원본 집계와 대조한다. 전체 데이터와 현재 page 합계를 혼동하지 않는다. 증거는 아래 **수치 대조 표** 형식으로 남긴다. 최소 두 조건(기본 필터/기간 + 변경한 필터/기간)을 대조하고, 불일치는 원인(집계 범위·반올림·시간대·페이지 합계)과 조치를 적는다.

   | 필터/기간 | 원본 집계(쿼리/API 값) | 카드 값 | 차트 값(대표 점) | 표 합계(현재 page / 전체 조건) | 일치 여부 |
   |---|---|---|---|---|---|
2. 기간/필터 변경, drill-down, sorting/pagination의 실제 범위를 확인한다. server pagination인데 현재 page만 정렬되는 회귀를 막는다(표 규칙은 [work-ui-surfaces.md](work-ui-surfaces.md) §1.3).
3. empty·한 건·음수·매우 큰 값·누락·느린 요청·오류 중 해당하는 상태를 확인한다. 요청 순서가 역전돼 오래된 값이 덮어쓰지 않는지 확인한다.
4. 좁은 화면·긴 범례·숫자 정밀도·tooltip clipping·keyboard/touch 접근을 확인한다. 핵심 값을 텍스트나 표로도 읽을 수 있게 한다.
5. 많은 데이터가 실제 요구이면 대표 규모에서 렌더·필터 반응을 측정한다. 가상화/샘플링은 선택·focus·내보내기·수치 의미를 보존하는지 함께 검증한다.
6. 레거시 엔진에서 이관한 차트는 위 parity 항목을 이전 엔진 결과와 대조하고 완료 증거 표를 채운다. 개별 차트 예외가 없는 route에서 필수 parity 항목이 미실행이면 `이관(parity 미실행)`, 실패이면 `이관(parity 실패)`로 기록하고 `이관 완료`로 적지 않는다. 개별 차트 예외가 있는 route는 `기록된 예외`를 유지하고 이관한 차트의 parity 미실행·실패 항목·사유·해소 계획을 별도로 기록한다. 어느 경우에도 필수 검증 공백을 검증 완료로 처리하지 않는다.
7. 새 차트 방향은 선택한 공식 예제와 결과를 같은 대표 행동의 시작/전환/끝 상태로 대조한다([verification.md](verification.md)).

시각 스냅샷만으로 데이터 정확성까지 통과했다고 보고하지 않는다.
