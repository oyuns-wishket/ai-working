# 불만족 원인을 확인하고 필요한 곳을 개선하기

사용자가 “밋밋하다”, “생각한 것과 다르다”, “버벅인다”처럼 결과에 불만을 표시하면 읽는다. 완료 보고 뒤의 피드백도 기존 목표와 승인을 이어받는다. 수정 전에 실제 결과와 승인 시안/요청을 같은 route·viewport·data·state·theme·auth와 장면·행동·기기 조건에서 대조한다. 취향 수정은 오류일 필요가 없고, build 통과가 만족도를 증명하지도 않는다.

게이트·도구 기본값은 [SKILL.md](../SKILL.md), 재검증 강도·증거 형식은 [verification.md](verification.md)를 따른다. `small-feature`라는 이유로 재현·수정·검증 강도를 낮추지 않는다.

## 원인에 맞는 수정

| 관찰한 차이 | 먼저 할 일 | 기록할 곳 |
|---|---|---|
| 느낌·구도·밀도·속도·강조가 취향과 다름 | 구체적인 장면/전환 차이를 짚고 해당 시안·디자인을 수정한다. 기술 수치 대신 체험할 수 있는 차이로 제안 | 프로젝트 DESIGN/기존 결정 기록 |
| 승인한 동작이 빠지거나 입력·상태·export가 잘못됨 | 재현 후 코드·자산·통합 원인을 수정; 원인 불명은 systematic-debugging 적용 | 구현노트와 필요한 회귀 검증 |
| 기기에서 느림·깨짐 | frame/seek/decode·메모리·network·lifecycle을 측정하고 병목을 수정 | 조건·전후 측정·대안 차이 |
| 자료/도구 권한 부족으로 의도를 재현할 수 없음 | 실제 차이와 가능한 무료/포함 유료 경로를 구체화; 핵심 경험 변경은 선택받음 | 제작/기능 권한 결정 |
| workflow가 필요한 질문·검수·경로를 누락해 같은 실패를 유발 | 현재 결과를 먼저 고치고 일반화할 수 있는 지침 결함을 최소 변경으로 정리 | 승인된 공통 skill 개선 또는 후속 제안 |

“불만족”만으로 공통 스킬을 자동 수정하지 않는다. **재현된 지침 결함 또는 반복되는 누락**이 있어야 하고, 특정 고객의 취향·일회성 버그·개인 결제/계정 사실을 전역 기본값으로 만들지 않는다. 단 한 번의 사례도 지침의 모순/누락을 재현하면 개선 근거가 될 수 있다.

## 반복 범위와 공통 스킬 반영

1. “어느 장면이 어떤 기대와 다른가”를 기존 말·화면으로 구체화한다. 정보가 모자라면 결과를 바꾸는 질문만 하고, 명확한 결함은 같은 승인 범위에서 바로 수정한다.
2. 원인 가설과 수정할 대상, 확인할 대표 행동/상태를 적는다. 승인된 패턴의 작은 수정이면 기존 결정을 재사용한다. 승인 기록 없는 기존 코드도 새 표현이 아니면 원 코드·동작 동일성·새 표현 아님 판정 근거를 “기존 코드 패턴 재사용(미승인)”으로 기록하고 변경 상태를 검증한다. 새 표현 판정과 공식 예제 관찰 미완료 처리는 [SKILL.md의 공통 원칙](../SKILL.md#공통-원칙)을 따른다. 새 모션·차트·그래픽 방향이면 공식 관찰·채택 표현·같은 데이터/콘텐츠의 동작 시안 정확히 3개·실제 선택을 해당 범위에서 수행한다. 새 시각 세계관/대표 화면 전면 교체이면 full 게이트를 적용한다. 제작 방식·비용·핵심 기능이 달라지면 준비한 대안의 차이에 필요한 결정만 받는다. 기존 승인 범위를 이유 없이 초기화하지 않는다.
3. 범위 내 수정 후 해당 장면·상태·기기와 영향받는 검사만 반복한다. 새 실패 근거 없이 생성 호출·전체 검사·리뷰를 무한 반복하지 않는다. 유료 생성 한도는 [tool-capabilities.md](tool-capabilities.md)를 따른다.
4. 일반화할 스킬 결함이 확인되고 공통 개선이 현재 승인 범위에 있으면 `ssotify`로 기존 소유 참조를 수정한다. 관련 trigger뿐 아니라 명확한 요청·작은 변경·audit·기존 승인 재사용 같은 인접 사례도 검증한다. 이번 프로젝트 수정 권한만 있을 때는 공통 변경안을 구체화해 제안하고 프로젝트 수정은 계속한다.
5. 바뀐 결과를 직접 보여주고 요청한 느낌·행동을 사용자가 판단할 수 있게 한다. 합의한 수용 기준과 요청된 리뷰를 충족하면 종료하고 선택적인 추가 연출은 후속으로 분리한다. 사용자 답이 없거나 자동 검사만 통과했는데 “만족 확인”으로 기록하지 않는다.

기존 DESIGN의 Feedback correction 또는 구현노트에 아래 표를 남긴다. 재검증 결과는 공통 검증 증거 표를 링크해 실제 명령·route·조건·결과·미실행 사유를 확인할 수 있게 한다.

| 기대 | 관찰된 차이 | 원인/근거 | 수정 대상 | 재검증 | 사용자 결정 또는 미확인 |
|---|---|---|---|---|---|
| 요청/승인 시안 | 같은 route·viewport·data·state·theme·auth·장면·행동·기기 조건의 차이 | 취향/코드·자산/성능·권한/workflow | 변경과 승인 범위 | 같은 조건의 전후·영향받는 검사 | 실제 답변 또는 미확인 |

공통 스킬 변경을 제안하면 재현 사례·문제 문장·규칙 소유 파일·제안 변경과 현재 skill-edit 승인 범위를 함께 적는다. `audit`에서는 진단·개선 제안만 제공하며 코드·정본·공통 스킬을 쓰지 않는다. 스킬 수정 자체는 별도 디자인 시안 작업이 아니며, 재사용 지침의 검증·배포는 `ssotify`/`dev-protocol`의 기존 승인 범위를 따른다.
