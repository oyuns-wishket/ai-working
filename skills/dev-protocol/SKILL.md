# dev-protocol — 구체화 → 계획 → 실행 → 완료

## 목적

구현·디자인·비가역 작업을 다음 원칙으로 진행한다.

1. 착수 전 요구사항과 미정 결정을 확정해 재작업을 줄인다.
2. 작업마다 계획과 판단·이탈을 구현노트에 남긴다.
3. Git 작업은 격리 worktree를 기본값으로 삼아 멀티세션 충돌을 막는다.
4. 완료 시 퀴즈 없이 요구사항과 개선사항을 짧게 설명한다.
5. 사용자가 정한 배포 범위를 끝까지 수행하고, 안전하게 병합된 task worktree는 정리한다.
6. 배포가 검증된 **같은 턴**에 클로즈아웃한다: 사용자 관점 요약 재보고 + 개발 배포는 wiki 후보 적재, 운영배포 성공 후에만 `knowns`를 묻고 사용자의 한 번의 선택으로 wiki closeout을 끝낸다.

단순 조회·설명·재시도 가능한 read-only 작업에는 적용하지 않는다.

## 승인과 질문

1. **실제 사용자 요청·답변을 승인 근거로 쓴다.** 이미 분명한 요청에 확인 질문을 만들어내지 않는다. 모델·subagent가 사용자 답을 꾸미거나 미승인 범위를 승인으로 기록하지 않는다.
2. **승인은 같은 범위에서 유지된다.** `ㄱㄱ`, `진행해`, `알아서`는 직전에 구체화한 작업 범위에 적용한다. 명시한 배포에 필요한 단계는 §5.3에 따라 연속 수행하되, 새로운 운영 범위나 파괴적 변경으로 확대하지 않는다.
3. **일상적인 구현 선택은 직접 판단한다.** 기존 기능의 요구사항이 명확하면 가역적인 구현·검증 방법은 저장소 패턴과 사용자 의도로 정하고 근거를 기록한다. 새 제품의 중요한 동작·시각 방향은 필요한 사용자 결정을 받는다.
4. **결과를 바꾸는 미정 사항만 질문한다.** 정확성·범위·비가역 영향에 필요한 답을 추론할 수 없을 때만 짧게 묻는다. 답에 의존하는 변경은 기다리되 독립적인 조사·준비는 계속한다.
5. **첫 write 전에 근거를 남긴다.** 구현노트에 실제 요청·답변, 허용된 범위, 남은 미정 사항을 기록한다. 명확한 최초 요청이나 앞서 받은 답으로 충분하면 추가 인터뷰를 요구하지 않는다.

디자인 작업은 관련 디자인 skill의 방향 선택·시안 승인 gate도 함께 통과한다.

## 0. 기본 흐름

모든 비단순 개발을 아래 순서로 진행한다.

0. **이슈 연결**: 비단순 구현 또는 이슈가 지정된 작업은 [이슈 생명주기](references/issue-lifecycle.md)의 시작 절차로 기존 항목·진행 PR을 확인한다. 대표 이슈와 완료 조건을 연결하거나 `생략/조회 불가` 이유를 남긴다.
1. **구체화**: 현재 요청·기존 답변·코드로 결과와 범위를 정한다. 결과를 바꾸는 미정 사항만 질문한다.
2. **계획**: 변경 파일, 단계와 의존성, 수용 기준, 검증 명령을 정한다. 작은 수정은 짧게 기록하고, 여러 세션에 걸친 작업만 상세 계획으로 남긴다.
3. **실행**: 승인된 범위를 수행하고 실측 증거로 검증한다. 구현 중 새 범위가 드러나면 그 차이만 설명한다.

계획·실행·worktree·검증·branch 완료를 이유로 별도 generic skill을 연쇄 호출하지 않는다.
테스트 설계나 코드 리뷰가 필요한 작업에서만 [검증과 리뷰](references/verification-review.md)를 읽는다.
원인 불명 오류에는 `systematic-debugging`, 독립적인 병렬 lane에는 `multi-session-dev`를 추가한다. 이때 승인된 write 범위·commit 허용·task branch·수용 기준·검증 명령을 입력 계약으로 넘기고, 반환된 통합 결과·blocked 항목·남은 worktree를 이 프로토콜의 완료 절차에서 처리한다. 역방향 참조는 없다.
예전 brainstorming/writing-plans/executing-plans 요청도 위 단계로 처리하며 새 승인 절차를 만들지 않는다.
Docker/DB 자원을 띄우거나 HTML을 제공하거나 새 프로젝트 레이아웃을 명시 요청받았을 때만 [로컬 운영과 관례](references/local-operations.md)의 해당 절차를 읽는다. Migration 실행 표시가 필요하면 같은 문서의 migration 절차를 확인한다.

## 프로젝트 workflow skill과의 관계

저장소에 브랜치·PR·배포 절차를 고정한 skill이 있으면 그 절차를 따른다. 이 문서는 요구사항, 승인, 구현노트, 이탈, 완료를 소유하고 프로젝트 skill은 브랜치, 머지, 배포 mechanics를 소유한다. 두 문서가 같은 승인 대상을 다뤄도 사용자에게 두 번 묻지 않는다.

저장소의 `AGENTS.md`, `CLAUDE.md`, `.claude/rules/`, `.claude/skills/`를 먼저 확인한다.
기존 HANDOFF는 현재 `Next actions`, `Open items & blockers`, `Decisions & context`만 제한된 분량으로 읽는다.
설치된 `hooks/handoff-context.mjs` 또는 ai-working 정본의 같은 helper로 발췌할 수 있다.
잘린 내용·완료 이력은 이번 task에 필요할 때 원본의 해당 부분만 추가 조회하며, 전체 파일을 자동 주입하지 않는다.

프로젝트가 전용 시작·PR·배포 skill을 제공하면 그 절차를 읽고 이 공통 프로토콜과 함께 적용한다. 전용 skill 이름이나 고객별 배포 경로를 이 공통 문서에 하드코딩하지 않는다.

## 1. 요구사항 인터뷰

- 기존 기능은 요청·현재 코드·앞선 답으로 결과와 범위를 정할 수 있으면 바로 계획·구현한다. 명시하지 않은 모든 엣지케이스를 인터뷰 항목으로 만들지 않는다.
- 사용자에게 중요한 동작·우선순위·데이터 처리에 미정 사항이 있으면 필요한 질문만 한다. 이미 받은 답은 재사용하고 합리적으로 추론 가능한 세부사항은 직접 결정한다.
- 구현 범위를 정할 정보가 모이면 확정 사항을 짧게 요약하고 진행한다.
- 새 제품·디자인처럼 정본이 없으면 최소 한 번의 실제 사용자 답이나 명시적 요약 승인을 받는다.

## 2. 레퍼런스

말로 확정하기 어려운 새 UI·UX는 필요한 레퍼런스를 요청하고 중요한 방향을 확인한다. 기존 화면이나 첨부 자료를 보존하는 명확한 요청에는 같은 방향을 다시 묻지 않는다. 새 시각 방향·시안 승인이 필요한 작업은 디자인 skill을 따른다.

## 3. Git worktree 기본값

Git 저장소의 구현 작업은 작업별 branch와 별도 worktree에서 시작한다. 여러 세션이나 병렬 작업이 예상되면 반드시 격리한다.

다음 경우에만 생략하고 이유를 구현노트에 남긴다.

- read-only 또는 한 번의 안전한 설정 변경
- non-Git 작업
- 이미 해당 작업 전용 worktree에 있음
- 저장소의 강제 workflow가 다른 격리 방식을 지정함
- 기존 dirty 상태 때문에 안전하게 옮길 수 없음

worktree 생성 전 기준 branch, 새 branch 이름, 경로를 확인한다. 기존 작업과 겹치는 branch나 경로를 재사용하지 않는다. 미커밋·미병합 작업이 있는 worktree를 자동 삭제하지 않는다.

## 4. 구현노트

위치는 `<project>/docs/impl-notes/YYYY-MM-DD-<slug>.md`다. 시작 전에 기존 노트에서 비슷한 사건과 복병을 확인한다.

첫 write 전에 `## Gate evidence`를 작성한다. 계획에서 달라지는 순간 보수적인 대안(기존 동작 보존, 좁은 변경)을 택하고 `⚠️ DEVIATION`으로 표시한다.

```markdown
# YYYY-MM-DD <작업명>

## 목표 / 확정 사항
- (인터뷰 결과)

## Gate evidence
- 사용자 요청·답변: (현재 대화의 실제 내용)
- 확인 질문: 없음 / (남은 중요한 질문과 실제 답)
- 승인된 범위: (허용된 write)
- 미승인 가정: 없음 / (구현하지 않은 항목)

## Issue tracking
- 대표: <owner/repo#number 또는 생략/조회 불가 이유>
- 관련 이슈 / 이번에 처리할 완료 조건: <연결과 범위>
- 완료 시점: <구현·통합·개발배포·운영배포 중 실제 요구>

## 계획
- (단계와 검증)

## 판단 근거
- (선택과 이유)

## ⚠️ DEVIATION
- ⚠️ <이탈> → 대응: <대안과 근거> → 리뷰: 자체 확인 / 사용자 결정 필요·결과
- 없으면 `없음`

## 다음에 참고
- (재발 가능한 함정·패턴)
```

## 작업별 측정

ai-working의 `scripts/task_metrics.py`를 사용할 수 있는 비단순 구현 작업은 시작 시 task를 기록하고,
자신과 Worker의 로그를 확실히 식별할 수 있을 때만 `--session-log`로 연결한다. CWD나 시간대가 같다는
이유로 다른 세션을 묶지 않는다. 로그를 모르면 usage를 `unknown`으로 남기고 작업은 계속한다.
완료 시 실제 검증 결과로 `finish`하고, 재시도 횟수는 확인한 경우만 기록한다. 소요 시간은 대기까지
포함한 경과 시간이며 과금액·집중 작업 시간이 아니다. 단순 조회·문구 교체에는 새 측정 절차를 강제하지 않는다.
명령과 저장 경계는 [작업별 측정](../../docs/task-metrics.md)을 필요할 때 읽는다.

## 5. 완료 절차

구현과 검증이 끝나면 아래 절차를 수행한다. worktree 삭제는 문서·배포 closeout을 마친 뒤 마지막에 한다.

### 5.1 이탈 리뷰

- 승인 범위 안의 구현 방법 변경은 검증하고 근거를 기록한다. 요구사항·범위가 달라지거나 새 파괴적 변경·위험이 생겼을 때만 영향과 대안을 제시해 그 차이에 대한 결정을 받는다.
- 없으면 `계획 이탈 없음`이라고 보고한다.

### 5.2 간단 완료 보고

퀴즈나 이해도 문제를 내지 않는다. 이번 전달 범위가 끝났으면 §5.7로 이슈 상태를 대조한 뒤 아래 항목을 보고한다. 배포 등이 남아 있으면 이슈도 그 잔여 범위를 유지한다.

- **요구사항**: 사용자가 원한 동작과 범위
- **개선사항**: 실제로 달라진 동작과 사용자에게 생긴 이점
- **검증**: 실행한 build, lint, test와 결과
- **이탈**: 없음 또는 승인 대기 항목
- **이슈**: 연결 번호와 `종료/일부 완료/배포 대기/생략/조회 불가`, 관련 열린 항목

### 5.3 배포 범위 선택

**제품·앱 코드를 구현했고 실제 PR 또는 배포 workflow가 있으며 배포 범위가 아직 미정일 때만**, 검증된 결과를 보고한 뒤 다음 범위를 확인한다. 이미 `PR까지`, `개발서버 배포`, `운영까지` 등을 요청받았다면 그 범위를 재질문하지 않는다.

1. **PR까지** — 해당 변경의 commit·branch push·PR 생성/갱신
2. **개발서버 배포** — PR까지의 작업과 develop merge·비파괴적 개발 migration·개발 환경 검증
3. **개발 + 운영배포** — 개발 환경 검증 후 운영 배포 절차까지 수행

구체적으로 설명한 범위의 선택·배포 요청을 필요한 단계의 묶음 승인으로 기록한다. commit·push·merge·같은 범위 migration을 따로 재확인하지 않는다. migration dry-run은 직접 실행·보고하고 승인 범위와 일치할 때만 적용한다. 파괴적 데이터/스키마 제거, 예상 밖의 범위·위험, 새 운영 범위는 별도 확인한다. 실제 검증과 프로젝트의 branch·main merge 담당자 규칙은 유지한다. 없는 환경은 근거와 함께 생략한다.

옵션 2 또는 3을 실행했으면 배포 검증 증거를 수집한 **같은 턴**에서 §5.5→§5.6을 수행하고 §5.4의 안전 조건에 따라 정리한다. 클로즈아웃을 다음 사용자 프롬프트로 미루지 않는다.

글로벌 규칙, skill, 문서, 로컬 설정·도구 유지보수이거나 대상 저장소·PR·배포 workflow가 없으면 선택지를 만들지 않는다. `배포 대상 없음`이라고 한 줄로 보고하고 끝낸다.

### 5.4 worktree 정리

완료·HANDOFF 기록까지 보존한 뒤, 이번 task가 만든 worktree의 dirty·merge 상태와 다른 세션 사용 여부를 확인한다. 사용자가 유지를 요청하지 않았고 깨끗하며 대상 branch에 완전히 반영된 작업 전용 worktree·불필요한 local branch는 별도 선택 질문 없이 안전하게 정리하고 결과를 보고한다.

primary worktree, 다른 세션이 쓰는 경로, 미커밋·미병합 변경은 그대로 보존하고 이유만 보고한다. 강제 삭제하지 않으며, 불필요한 `정리/유지` 선택을 요구하지 않는다.

별도 task worktree를 만들거나 사용하지 않았다면 질문하지 말고 `정리 대상 worktree 없음`이라고 보고한다.

### Wiki 활용 기록

이번 작업의 `project-wiki-context` 조회가 trace ID를 반환했다면 검증 후 같은 trace에 실제 사용·미사용·누락·오류 결과를 기록한다. 절차는 [retrieval feedback](../project-wiki-context/references/retrieval-feedback.md)을 따른다. 문서가 검색됐다는 이유만으로 도움이 됐다고 판정하지 않고, 기존 검증 산출물에 판단 근거와 trace ID를 연결한다. 사용자 확인을 추가로 요구하지 않으며, 관측이 없거나 기록을 남길 수 없으면 unknown으로 남긴다. 이전 세션 trace를 추정해 연결하거나 wiki 관리·평가 결과를 실제 개발 성과로 합산하지 않는다.

### 5.5 HANDOFF

`docs/handoff/HANDOFF.md`가 없으면 ai-working `templates/HANDOFF.md`를 복사해 만든다. 세션 시작 hook이 `[인계 없음]`으로 부재를 알린다. 있으면 `Next actions`, `Decisions & context`, `Open items & blockers`를 갱신한다. 세 절 제목은 hook이 인식하는 이름·별칭을 유지한다.

### 5.6 배포 클로즈아웃 (같은 턴)

배포 범위 옵션 2(개발서버) 또는 3(운영)을 실행하고 배포 검증 증거를 확보한 경우에만 적용한다. 옵션 1(PR까지)이거나 배포가 실패·보류되면 적용하지 않는다.

Wiki 후속 선택이나 스킵 전에 §5.7로 연결 이슈를 정합화한다. Wiki 선택이 프로젝트 이슈 처리를 건너뛰게 하지 않는다.

1. **사용자 관점 컴팩트 요약 재보고**: §5.2 형식(요구사항·개선사항·검증·이탈)으로 배포 결과·검증 증거(배포 URL·헬스체크)와 함께 짧게 다시 보고한다.
2. **개발서버 배포까지인 경우**: 이번 작업의 durable delta(의미·목표·기여·판단 근거·재발 함정)를 `docs/handoff/HANDOFF.md`의 `## Wiki candidates`에 적재한다. 승인된 작업 범위 내 문서 write이므로 질문하지 않는다. canon wiki에는 쓰지 않는다 — 운영 검증 전 지식의 canon 오염을 막는 경계다.
3. **운영배포까지인 경우**: §6 `knowns`를 실행한다. `## Wiki candidates` 적재분을 knowns의 후보 입력에 포함하고, ingest된 항목은 같은 턴에 HANDOFF에서 제거한다(project repo 정리는 knowns가 아니라 이 skill의 책임이다).

### 5.7 이슈 정합성

[이슈 생명주기](references/issue-lifecycle.md)의 완료 절차로 연결한 이슈 각각의 현재 조건·PR/commit·검증·필요한 배포 결과를 대조한다. 충족한 범위는 기존 권한 내에서 종료하고 원격 상태를 재조회한다. 일부 완료·배포 대기·검증 불가이면 완료 증거와 남은 일을 갱신하고 열어 둔다. 작은 작업의 생략은 보고만 하며 종료용 이슈를 새로 만들지 않는다.

## 6. 운영배포 후 knowns wiki closeout

운영배포 검증에 성공한 경우에만 [운영 클로즈아웃](references/production-closeout.md)을 읽고 같은 턴에 실행한다.
개발배포는 §5.6의 HANDOFF 후보 기록까지만 수행한다. PR·설정 관리·wiki 관리 자체에는 운영 클로즈아웃을 적용하지 않는다.

## Gate 위반 복구

실제로 필요한 승인이 없었으면 해당 범위의 추가 write·배포를 멈추고 미승인 부분과 필요한 결정을 설명한다. 앞서 받은 승인이 있으면 기록을 보완하고 재질문하지 않는다. 승인된 독립 작업은 계속하며, `knowns` 질문은 단일 묶음으로 처리한다.
